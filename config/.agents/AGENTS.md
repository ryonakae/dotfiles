## 応答・記述

- チャットでの応答は日本語。システムエラーやログの引用は原文のまま
- ドキュメント、コード内コメント、コミットメッセージは、既存方針を優先しつつ、公開リポジトリでは英語、非公開リポジトリでは日本語を基本とする
- コメントは Why だけ。処理内容の説明は書かない

## 作業の進め方

- 実装前に、関連する仕様・設計・計画・決定記録を読む
- コードやドキュメントで確認できることは確認し、解消できない曖昧さだけ質問する
- 依頼や計画にない変更は、始める前に確認する
- 破壊的操作・機密情報へのアクセス・権限やセキュリティ設定の変更は要事前承認
- コードの確認・修正は、まず lint・format・型チェック・テストで機械的に検出・修正できる問題を処理し、その結果を踏まえて進める
- 通過した検証は、新たな変更や懸念がある場合だけ再実行する
- 複雑な要件の整理や重要な設計判断が必要な実装は、`dig` → 承認 → `plan` → 承認 → `implement` で進める
- テストが整備されているプロジェクトでは `tdd` スキルで実装する

## 実装方針

- 既存コードの設計・記法に従う
- KISS: 要件を満たす最も単純な実装にする
- YAGNI: 現在の要件に不要な機能・抽象化・依存を追加しない。既存実装・標準機能・導入済み依存で足りるか先に確認する
- DRY: 同じ知識・判断を重複させない。ただし偶然似ているコードを無理に共通化しない
- SRP: 一つの部品に異なる責務を混在させない
- バグ修正は根本原因を直す。共通処理を変更するときは呼び出し元への影響を確認する
- 後方互換・データ移行・非推奨経路の維持は、依頼されたか、既存の利用者やデータのために必要な場合だけ行う
- 不要になったコード・テスト・記述は同じ変更で削除する。移行に必要な場合を除き、削除済みのものへの言及や過去との比較を残さない
- テストは現在の仕様で守るべき振る舞いのために残す。削除の事実だけを確認する検証は作業中に行い、恒久テストにしない

## ツール・環境

- 未確認のオプションや環境変数の挙動を推測して使わず、ヘルプや公式ドキュメントで確認する
- 作業開始前に `HERDR_ENV` を確認し、`1` なら `herdr` スキルを読んで、必要に応じてペイン・タブなどを操作する
- ユーザーに提示するシェルコマンドや環境変数設定は、指定がない限り `fish` の構文で記述する
- worktree の操作は `git worktree` を直接使わず、`wt`（Worktrunk）と `use-worktrunk` スキルで行う
- Python: CLI ツールは `uvx`、スクリプトは `uv run`、パッケージ追加は `uv add`
- iOS Simulator での UI 動作検証や `.ad` テストの作成・実行は、`use-agent-device` と `agent-device` スキルで行う。配置・初期状態・実行方法は対象アプリの既存規約を優先する

### ドキュメント・Web検索

- ライブラリ/API のドキュメントは `find-docs` スキルで参照する
- Web検索・ページ取得・公開コード検索は `ketch` スキルに従い、CLI で行う。一次情報を優先し、取得件数・文字数を必要な範囲に制限する
- UI 操作や Ketch で取得できないページの確認には `agent-browser` を使う
