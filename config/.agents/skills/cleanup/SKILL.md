# Cleanup

現在の仕様を理解・利用・保守するために必要なものだけを残す。削除した事実を説明として残すと、読み手は不要になった概念まで理解しなければならない。不要な説明は別の説明へ置き換えず、そのまま消す。

## 承認

- コマンドの実行は調査開始の指示であり、修正・削除の承認ではない。承認前は読取調査と非破壊の検証、この作業が所有する `CLEANUP.md` の作成・更新だけを行う。自動修正・生成物更新・ファイルの削除や移動は行わない。
- 対象パス、変更・削除内容、根拠、検証方法を整理案として提示し、ユーザーの明示的な承認を待つ。完了時の `CLEANUP.md` 削除も案に含める。承認された項目だけを実行し、追加候補や承認範囲の変更は再度確認する。
- 承認内容と対応するユーザー発言を `CLEANUP.md` に記録する。起動、調査依頼、エージェント自身の判断を承認に読み替えない。再開時も承認範囲が確認できなければ修正・削除せず確認する。

## 判断の基準

次の観点をそれぞれ確認する。事実として正しい記述も、現在必要でなければ整理対象になる。

| 観点 | 探すもの |
| --- | --- |
| 削除・変更の痕跡 | 「Xは削除済み」「Xは使わない」「以前はXだった」「Yは変更していない」、不要な新旧比較、削除した事実だけを固定するテスト |
| 役目を終えたもの | 未使用の実装・helper・付属物、古い手順、現行仕様と食い違うテスト、不要な重複 |
| 追加の意味を持たない説明 | 設定・コード・仕組みですでに担保され、利用や判断に必要な情報を加えていない言い直し |

- 「これを消すと、現在必要な動作・判断・利用手順の何が失われるか」を根拠とともに確かめる。削除件数や行数の削減を目標にしない。
- 現在必要な公開契約、移行・互換性、データ保護、設計理由、出自・ライセンスを保持する。履歴そのものが目的の記録は、現行手順に混ざった変更履歴と区別する。
- 説明は、何がすでに設定・コード・仕組みで担保されているかを確かめ、読み手に追加で何を伝える必要があるかで判断する。言い換えや汎用化で残す前に、記述自体の必要性を問う。実装と重なるだけで不要とせず、読み手に必要な利用説明・制約・設計理由は保持する。
- 固定データを保存する必要があっても、その付属READMEに動かないコマンドや古い手順を残す理由にはならない。データと説明を別々に判断する。
- テストの必要性と、その名前・入力・期待値の妥当性を分けて確認する。未知キー拒否などの現行契約を残し、廃止名を使う必要のないケースや重複だけを整理する。不在そのものが現在の契約・安全要件なら、そのテストは残す。

## 1. 対象と記録を用意する

1. 適用される指示、仕様、検証手順と作業ツリーの差分を確認する。他者の変更を保持し、所有権が不明な箇所は編集しない。機密ファイルを探索・記録へ取り込まない。
2. 調査範囲を定める。指定範囲があれば尊重し、リポジトリ全体の依頼を差分だけの確認へ狭めない。整理を求める引数があっても、まず調査と整理案の提示まで行う。
3. ルートの `CLEANUP.md` を確認する。同じ作業の実ファイルなら読み込んで再開する。無関係な既存ファイル、symlink、所有権が不明な記録なら変更せず、保存先をユーザーに確認する。存在しなければ今回の作業記録として作成する。ignore設定は変更しない。
4. 対象ファイルを列挙して範囲を把握する。実装、テスト、文書、エージェント指示、自作スキル、付属README、設定内の注記など、存在するものを対象に含める。キーワードのヒット一覧を対象一覧の代わりにしない。Git管理外のソースも対象範囲なら含め、ビルド生成物などと区別する。列挙結果をそのまま `CLEANUP.md` に転記する必要はない。
5. 外部管理物、バイナリ、数値配列などは役割に応じて除外または注記だけの確認に分け、理由を残す。履歴文書は役割を確認せず丸ごと除外しない。作業用の `CLEANUP.md` 自体は整理対象から除く。
6. 既存のlint・型検査・テストなどで分かる問題は、対象に近い非破壊の検証から先に把握する。有効な実行結果があれば再利用する。承認前にformatterの自動修正やsnapshot更新を実行しない。

## 2. 読んで根拠を確かめる

- リポジトリの構成と各領域の役割を把握し、現在の動作・利用・保守に直接関わるものから確認する。それ以外は役割と関連性に応じて順序を決める。特定の文書種別やディレクトリ構成を前提にせず、存在しない種類の資料を探すためだけに調査を広げない。
- 各対象を全文読む。長いファイルは分割する。切り詰め・検索結果・抜粋だけで「確認済み」にしない。数値JSONの文字列注記だけを読んだ場合は、その範囲を明記する。取得行範囲の逐一記録は不要だが、途中で中断する場合は続きの位置を残す。
- 各ファイルを上記の判断観点で確認し、現行実装・呼び出し元・公開入口・設定・対応テストと照合する。検索は参照や候補の発見を補助するために使う。
- 名前や検索ヒットの少なさだけで未使用と決めない。動的な利用、公開API、運用からの利用、保存データへの必要性を確認する。Git履歴などの追加調査は判断に必要な箇所に絞る。
- 各領域を確認した後、ファイルや領域をまたぐ不要な重複も確認する。同じ手順の多重管理、同じ契約を意味の違いなく固定するテスト、使い分ける理由を失った補助処理などを、利用者・責務・制約の違いと照合する。似ているだけのものを統合しない。
- 指摘には場所、不要または不整合と判断する根拠、残すべき契約、最小の対応を記録する。事実の確認と、削除してよいという判断を分ける。根拠が足りない候補は、判断に必要な追加情報とともに保留にする。
- 領域の確認・修正の一区切りごとに `CLEANUP.md` の進捗と次の作業を更新する。正常なファイルを一件ずつ記録せず、途中の領域では確認済みと未確認を区別できる位置や残りの対象を残す。compact直前まで記録を後回しにしない。
- 分担する場合は担当を重複させず、子に確認範囲・未確認部分・指摘の根拠を報告させる。親は担当範囲の抜けを確認し、指摘を参照元やテストなどで検証して統合する。子の「読了」「完了」という報告だけで完了扱いにせず、読取証明の台帳作成や全ファイルの再読は求めない。修正を分担した場合は実際の差分も確認する。
- 区切りでは、採用可能な整理案、判断待ち、重要な保持判断、未確認範囲を簡潔に報告する。再開用の記録をそのまま会話へ繰り返し出さない。

## 3. 整理案の承認後に実行・検証する

調査結果と整理案を提示して承認を待つ。調査だけの依頼なら報告で止める。以下は承認を得た項目に限って行う。

- 不要な実装・テスト・記述を、承認された関連箇所と一緒に削除する。必要な振る舞いは、過去を知らなくても分かる現在の条件・名前・手順で表す。不要な歴史を新しい文書へ移すだけの対応はしない。
- 「削除した」「もう考慮しなくてよい」「整理済み」などの注記や、削除完了だけを証明する恒久テストを追加しない。判断理由は作業記録と報告に集める。
- 仕様を勝手に変えない。必要性が不明な互換処理、動作変更を伴う整理、データ損失の懸念は調べ、解消できなければユーザーに確認する。好みによる再設計・抽象化・新しい仕組みを追加しない。
- 変更に近い既存テスト、構文・lint・型検査、リンク・参照元、必要なら生成元との整合を確認する。テスト自体を整理した場合は、残したテストが意図した条件まで到達し、現在の契約を守ることも確認する。
- 差分を読み、削除により未使用になった補助物、切れた参照、説明の残片、不要な注記の再追加を確認する。削除の完了確認はこの作業中に行う。
- 成功済みの検証は、後続の変更で無効になった範囲だけ再実行する。失敗・未実行・skipを成功扱いにしない。commit・pushは別途依頼された場合だけ行い、`CLEANUP.md` は含めない。

## 4. 再開と完了

- 再開時はまず `CLEANUP.md` の進捗と承認範囲を読む。記録した時点からのGit差分や作業ツリーの状態などで追加・削除・変更を確認し、影響する範囲を読み直す。未コミット・Git管理外の変更など、記録だけでは変更範囲を判断できない場合は、その領域を再確認する。変更により整理案が変わるなら再承認を得る。過去の検証結果も、対象の変更で無効になっていないか確かめる。
- 自分の修正後も差分と必要な検証を確認するまで完了にしない。他者による変更との競合は上書きせず確認する。
- 完了判定は「見つかった指摘を修正したか」だけでなく、「対象を確認し終えたか」で行う。未読・未取得、要修正、判断保留、必要な検証待ちがあれば、未完了として記録と次の作業を残す。
- 調査だけなら対象の確認と指摘・保留の報告までが完了範囲。整理を続ける予定があれば同じ記録を保持する。確認範囲を超えるゼロ保証はしないが、それを理由に依頼された確認を省略しない。
- 完了時は確認範囲、整理内容または調査結果、保持判断、検証結果と限界を報告する。継続作業がなく、記録の削除も承認済みなら、この作業が所有する `CLEANUP.md` だけを削除する。未承認なら保持して削除の可否を確認する。

## CLEANUP.md の記録形式

会話履歴がなくても次の作業と承認範囲が分かる、短い引継ぎとして残す。全ファイルの監査台帳にはしない。正常なファイルの個別行、SHA-256、取得行範囲の逐一記録、逐語的な作業日誌や長いログは不要。特別な保持判断が必要なときだけ理由を書く。

```markdown
# Cleanup 作業記録

## 範囲・進捗
- 依頼、調査のみ/整理、対象、除外と理由
- 今回の作業識別情報、進捗記録時のHEADと既存差分の要点
- 確認済みの領域、未確認範囲、次に読む場所・行う作業

## 候補・保留
- 場所、根拠と照合先、残す契約、対応案と検証方法
- 判断に足りない情報、重要な保持判断、対応状況

## 承認
- 承認された項目・操作と対応するユーザー発言
- CLEANUP.md削除の承認有無

## 検証
- コマンド、対象とその版、結果、未検証事項
- 長いログは必要な場合だけ保存先を記録
```

読む作業の進捗と候補への対応状況を分け、未確認・承認待ち・修正済みで検証待ちなどを混同しない。再開位置は必要な粒度で残し、記録の維持自体が作業の中心にならないようにする。
