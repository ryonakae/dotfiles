# Cleanup

現在の仕様を理解・利用・保守するために必要なものだけを残す。削除した事実を説明として残すと、読み手は不要になった概念まで理解しなければならない。不要な説明は別の説明へ置き換えず、そのまま消す。

## 判断の基準

次の二つを別々の観点で確認する。事実として正しい記述も、現在必要でなければ整理対象になる。

| 観点 | 探すもの |
| --- | --- |
| 削除・変更の痕跡 | 「Xは削除済み」「Xは使わない」「以前はXだった」「Yは変更していない」、不要な新旧比較、削除した事実だけを固定するテスト |
| 役目を終えたもの | 未使用の実装・helper・付属物、古い手順、現行仕様と食い違うテスト、不要な重複 |

- 「これを消すと、現在必要な動作・判断・利用手順の何が失われるか」を根拠とともに確かめる。削除件数や行数の削減を目標にしない。
- 現在必要な公開契約、移行・互換性、データ保護、設計理由、出自・ライセンスを保持する。履歴そのものが目的の記録は、現行手順に混ざった変更履歴と区別する。
- 固定データを保存する必要があっても、その付属READMEに動かないコマンドや古い手順を残す理由にはならない。データと説明を別々に判断する。
- テストの必要性と、その名前・入力・期待値の妥当性を分けて確認する。未知キー拒否などの現行契約を残し、廃止名を使う必要のないケースや重複だけを整理する。不在そのものが現在の契約・安全要件なら、そのテストは残す。

## 1. 対象と記録を用意する

1. 適用される指示、仕様、検証手順と作業ツリーの差分を確認する。他者の変更を保持し、所有権が不明な箇所は編集しない。機密ファイルを探索・記録へ取り込まない。
2. 依頼の範囲と目的を定める。調査依頼なら洗い出しだけ、整理依頼なら根拠確認・修正・検証まで行う。指定範囲があれば尊重し、リポジトリ全体の依頼を差分だけの確認へ狭めない。
3. ルートの `CLEANUP.md` を確認する。同じ作業の実ファイルなら読み込んで再開する。無関係な既存ファイル、symlink、所有権が不明な記録なら変更せず、保存先をユーザーに確認する。存在しなければ今回の作業記録として作成する。ignore設定は変更しない。
4. 対象ファイルを列挙して記録する。実装、テスト、文書、エージェント指示、自作スキル、付属README、設定内の注記を含める。キーワードのヒット一覧を対象一覧の代わりにしない。Git管理外のソースも対象範囲なら含め、ビルド生成物などと区別する。
5. 外部管理物、バイナリ、数値配列などは役割に応じて除外または注記だけの確認に分け、理由を残す。履歴文書は役割を確認せず丸ごと除外しない。作業用の `CLEANUP.md` 自体は整理対象から除く。
6. 既存のlint・型検査・テストなどで分かる問題は、対象に近い検証から先に把握する。有効な実行結果があれば再利用する。調査のみの依頼では自動修正しない。

## 2. 一つずつ読んで根拠を確かめる

- 各対象を全文読む。長いファイルは分割し、取得範囲を記録する。切り詰め・検索結果・抜粋だけで「確認済み」にしない。数値JSONの文字列注記だけを読んだ場合は、その範囲を明記する。
- 各ファイルを二つの判断観点で確認し、現行実装・呼び出し元・公開入口・設定・対応テストと照合する。検索は参照や候補の発見を補助するために使う。
- 名前や検索ヒットの少なさだけで未使用と決めない。動的な利用、公開API、運用からの利用、保存データへの必要性を確認する。履歴の調査は判断に必要な箇所に絞る。
- 指摘には場所、不要または不整合と判断する根拠、残すべき契約、最小の対応を記録する。事実の確認と、削除してよいという判断を分ける。根拠が足りない候補は保留にする。
- ファイル確認・修正の一区切りごとに `CLEANUP.md` を更新する。compact直前まで記録を後回しにしない。
- 分担する場合は担当を重複させず、親が取得範囲・根拠・実際の差分を確かめて記録を統合する。子の「読了」「完了」という報告だけを根拠にしない。

## 3. 整理して検証する

調査だけの依頼なら、根拠付きの指摘と保留事項を報告し、修正へ進まない。

- 不要な実装・テスト・記述を関連箇所と一緒に削除する。必要な振る舞いは、過去を知らなくても分かる現在の条件・名前・手順で表す。不要な歴史を新しい文書へ移すだけの対応はしない。
- 「削除した」「もう考慮しなくてよい」「整理済み」などの注記や、削除完了だけを証明する恒久テストを追加しない。判断理由は作業記録と報告に集める。
- 仕様を勝手に変えない。必要性が不明な互換処理、動作変更を伴う整理、データ損失の懸念は調べ、解消できなければユーザーに確認する。好みによる再設計・抽象化・新しい仕組みを追加しない。
- 変更に近い既存テスト、構文・lint・型検査、リンク・参照元、必要なら生成元との整合を確認する。テスト自体を整理した場合は、残したテストが意図した条件まで到達し、現在の契約を守ることも確認する。
- 差分を読み、削除により未使用になった補助物、切れた参照、説明の残片、不要な注記の再追加を確認する。削除の完了確認はこの作業中に行う。
- 成功済みの検証は、後続の変更で無効になった範囲だけ再実行する。失敗・未実行・skipを成功扱いにしない。commit・pushは別途依頼された場合だけ行い、`CLEANUP.md` は含めない。

## 4. 再開と完了

- 再開時はまず `CLEANUP.md` を読む。対象一覧と実際のファイルを照合して追加・削除を反映し、確認時のhashと現在の内容が異なるファイルは再確認対象に戻す。過去の検証結果も、対象の変更で無効になっていないか確かめる。
- 自分の修正後も差分と必要な検証を確認するまで完了にせず、記録のhashを更新するだけで確認を済ませない。他者による変更との競合は上書きせず確認する。
- 完了判定は「見つかった指摘を修正したか」だけでなく、「対象を確認し終えたか」で行う。未読・未取得、要修正、判断保留、必要な検証待ちがあれば、未完了として記録と次の作業を残す。
- 調査だけなら対象の確認と指摘・保留の報告までが完了範囲。整理を続ける予定があれば同じ記録を保持する。確認範囲を超えるゼロ保証はしないが、それを理由に依頼された確認を省略しない。
- 完了時は確認範囲、整理内容または調査結果、保持判断、検証結果と限界を報告する。継続作業がなければ、この作業が所有する `CLEANUP.md` だけを削除する。記録を残して保守対象を増やさない。

## CLEANUP.md の記録形式

会話履歴がなくても次の作業を決められる情報を残す。正常なファイルは状態と確認範囲だけでよく、特別な保持判断が必要なときだけ理由を書く。逐語的な作業日誌や長いログは不要。

```markdown
# Cleanup 作業記録

## 目的・範囲
- 依頼、調査のみ/整理、対象、除外と理由
- 作業開始時のHEAD・既存差分、今回の作業識別情報

## ファイル確認
| パス | 状態 | 確認範囲・確認時SHA-256 | 指摘・保持理由 |
| --- | --- | --- | --- |

## 指摘・対応
- 場所、根拠と照合先、残す契約、対応、未解決事項

## 検証
- コマンド、対象とその版、結果、ログの場所（必要な場合）

## 次の作業
- 再開位置、保留中の判断、残りの検証
```

状態は未読／確認済み／要修正／修正済み・検証待ち／完了／保留など、読む作業と直す作業を区別できるものにする。ファイル一覧・指摘・検証の詳細は必要な部分を分割して読み、未確認部分を見失わない。
