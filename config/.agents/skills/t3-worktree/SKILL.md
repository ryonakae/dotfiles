# t3-worktree

`use-t3-code` の[作業場所の判断](../use-t3-code/SKILL.md#作業場所を判断する)で worktree を検討することになった後の手順。リポジトリが作業場所の手順を独自に持つ場合（スキル、AGENTS.md の記述など）は、この手順ではなくそちらに従う。

worktree の作成・移動・削除は T3 Code で行い、`git worktree` や内蔵の worktree 機能（Claude Code の `EnterWorktree` など）を使わない。これらで作った worktree はスレッドに紐付かない。T3 のツールが使えなければ、その制約を伝える。

- 作業中のスレッドを移す: `t3_worktree_handoff`（この手順）
- 別スレッドや子タスクを worktree で動かす: `t3_thread_launch` の `workspaceStrategy`、`delegate_task` の `isolation`
- 削除: 手動で消さない。T3 の設定 `storageCleanup` により、T3 Code がスレッドの削除・PR のマージ時に片付ける。未コミットの変更がある worktree は残る

worktree の作成に push・PR 作成・マージは含めない。それらは頼まれたときに [t3-merge](../t3-merge/SKILL.md) で行う。

## 1. 現在の場所を確認する

`t3_worktree_status` でスレッドの紐付け・ブランチ・パスを、`git status --short` で既存の変更を確認する。

- すでに今回の依頼の worktree にいる: そのまま続ける。ターンごとや工程の切り替わりで作り直さない。
- 別の依頼の worktree に紐付いている: `t3_worktree_handoff` は worktree を持つスレッドでは失敗する。使い回したり別の場所へ移したりせず、新しいスレッドで始める必要があることを伝える。軽微な関連修正はそのまま進めてよい。

新しい依頼か同じ作業の続きかは、スレッド名だけでなく会話と差分から判断する。

## 2. プロジェクト設定を確認する

`t3_project_read` で、このプロジェクトの `defaultThreadEnvMode` と `scripts` を読む。

| `defaultThreadEnvMode` | 進め方 |
|---|---|
| `local` | ユーザーが worktree を明示していなければ提案せず、現在の場所で進める。他の作業の未コミット変更は混ぜず、重なって安全に分けられない箇所だけ確認する |
| 未設定 | 次へ進む |
| `worktree` | スレッドが worktree に紐付いていれば手順1のとおり続ける。紐付いていなければ次へ進む |

`scripts` に `runOnWorktreeCreate` が有効なものがあれば、worktree の準備は整備済みとして手順4へ進む。

## 3. 準備が要るリポジトリかを確かめる

準備スクリプトが登録されていない場合だけ、次の兆候を確認する。

- 依存の lockfile（`package-lock.json`、`pnpm-lock.yaml`、`uv.lock`、`Gemfile.lock`、`Podfile.lock` など）
- primary checkout に実在する Git 除外ファイルのうち、動作に要るもの（`.env`、証明書、鍵など）。名前だけを見て、中身は読まない
- `.gitattributes` の Git LFS 指定

兆候がなければ準備不要として、何も聞かずに手順4へ進む。兆候があれば未整備として扱い、手順5の提案に初期整備を含める。

## 4. 基点とブランチ名を決める

- 独立した依頼: `origin` の既定ブランチ。`git symbolic-ref --short refs/remotes/origin/HEAD` で調べ、得られなければ `gh repo view --json defaultBranchRef` で確かめる。ローカルの既定ブランチの checkout や pull は要らない
- ユーザーが基点を指定した依頼、未マージの作業ブランチを前提とする続き: そのブランチ
- リモートがないリポジトリ: ローカルの現在のブランチ

一意に決まらなければユーザーに確認する。

ブランチ名は目的に合う短い名前にする（`feat/...`、`fix/...`、`docs/...` など）。リポジトリの既存ブランチの命名に合わせ、既存名と衝突したら別名にする。

## 5. 提案して承認を待つ

worktree を作成する理由・基点・ブランチ名を示し、承認を待つ。確認中は読取調査までにとどめ、dig log・Plan・コードの編集は移動後に行う。

未整備の場合は、同じ提案の中で初期整備の内容も項目ごとに示し、worktree の作成と整備を別々に承認できるようにする。「今回は準備なしで進める」も選べるようにする。

ユーザーがその依頼で worktree を明示している場合は、作成は承認済みとして扱い、基点とブランチ名を示してそのまま進める。初期整備の承認は別に要る。

## 6. 初期整備（未整備で、承認されたとき）

worktree は基点のブランチから作られる。準備スクリプトは基点に入っていないと新しい worktree に存在しないので、handoff より先に整備する。

整備の内容:

1. 準備スクリプトを用意する。リポジトリに既存のものがあれば使う。なければ、手順3の兆候に対応する処理だけを書く（依存の導入、Git 除外ファイルのコピー、LFS の展開）。準備済みなら何もせず終わるようにする
2. 既定ブランチへ commit・push する
3. `t3_project_update` で `scripts` に登録する（`runOnWorktreeCreate: true`）。`scripts` は配列全体を渡すので、既存のスクリプトを残して足す
4. GitHub のマージ時ブランチ自動削除が無効なら、有効にする

提案には、既定ブランチへ直接 push すること、T3 のプロジェクト設定を変えること、GitHub の設定を変えることを、それぞれ明示する。承認された項目だけを行う。

守る条件:

- 現在の場所で整備してよいのは、既定ブランチにいて、他の作業の未コミット変更がなく、開始前からの未 push の commit がない場合だけ。満たさなければ現在の場所では整備せず、準備なしで進めるか、整備を先に別の依頼として行うかを確認する
- push するのは整備の commit だけ
- Git 除外ファイルをコピーする場合は、対象のファイル名を提案に列挙して承認を得る。対象は Git 除外されている通常ファイルに限り、コピー先の既存ファイルを上書きせず、中身を出力しない
- 登録と handoff の前に、handoff の基点に準備スクリプトが存在することを確かめる。未マージの作業ブランチが基点でスクリプトがなければ、準備は移動後に手動で行うことを伝える

T3 のプロジェクト設定はマシンごとに保存される。別の PC では、リポジトリにスクリプトがあっても未登録になるので、同じ手順で登録だけを提案する。

## 7. スレッドを移す

承認された内容で、`t3_worktree_handoff` をそのターン最後のツール呼び出しとして実行する。

- `branch`: 決めたブランチ名
- `baseRef` と `startFromOrigin`: `origin` のブランチが基点なら `true`、ローカルのブランチが基点なら `false`
- `continuationPrompt`: 元の依頼、確定した判断、次の作業、参照文書、必要なローカル資料の絶対パス。実装前の相談中ならその段階も残す。秘密の値は書かない

未コミットの変更と Git 除外ファイルは移動先へコピーされない。変更は元の場所に残し、stash・commit・上書きで運ばない。今回の依頼に要る未コミットの資料は、移動先から元の絶対パスで読めるようにする。未コミットのコード変更を土台にする必要がある場合は、移し方を先に確認する。

## 8. 移動後に確かめる

返されたパス・ブランチと `startedFromOrigin` を確認する。準備スクリプトがあるリポジトリでは、その完了を確かめてから継続プロンプトの作業を再開する。準備が失敗した場合は実装を始めず、原因を報告する。
