# サブエージェントへの委譲

内容: 委譲するか決める、作業ディレクトリの共有・隔離、依頼と結果の確認、モデル × 思考レベルの選定（使用量の確認、文章作成の優先方針、共通の選定手順、指定方法）。

## 委譲するか決める

次のいずれかに当てはまれば委譲する。

- **並列化**: 互いに依存しない、それぞれまとまった量の作業が複数ある。
- **文章の品質**: 文章作成・推敲・ドキュメント更新は、下記の Gemini 優先方針に従って積極的に委譲する。誤字・数値・リンクの機械的な修正だけなら直接処理してよい。
- **観点の分散**: 自分の変更のレビュー、複数案からの設計判断、原因を絞り込めない不具合の仮説検証で、メインの見方に引きずられない評価がほしい。数行の自明な変更は除く。目的に応じて provider を選ぶ。
  - モデル固有の偏りを補う: メインと別のモデル系統（Claude・GPT・Gemini）を使う provider
  - 会話の文脈だけを切り離す、同じモデルでも同じ結論になるか確かめる: メインと同じ provider
  - 判断の影響が大きい: 異なるモデル系統に同じ依頼を出し、結果を比べる

次は、期待する利益が起動・文脈共有・結果待ち・親による検証の負担を上回る場合に委譲する。

- **速度・費用**: 範囲と報告形式を限定した調査などを、必要な品質を保ちつつ、メインより高速・低コストなモデル × 思考レベルで処理できる。
- **品質向上**: 難しい判断や重要なレビューを、そのタスクでメインより高い品質を見込めるモデル × 思考レベルに任せる。

## 作業ディレクトリの共有・隔離を決める

子タスクは原則として親の作業ディレクトリを共有する（`shared`）。複数の変更状態を同時に保持する必要があるときに `worktree` を選ぶ。委譲前に、親と他の子タスクの編集・検証への干渉を確認する。

- **worktree が必要になる場合**: 相互に干渉する並列編集、異なる実装案をそれぞれ保持して比較する試作、親が編集を続ける間の固定コミットの検証、子ごとに独立したブランチ・PRを作る作業。
- **shared で進める場合**: 読むだけの調査、親が対象の編集を止めている間のレビュー、順番に行う修正。担当ファイルが別でも、依存関係や生成物・ビルド出力の競合を確認する。出力先の分離や実行順の調整で干渉を避けられるなら、新しい worktree は作らない。

レビューの独立性は作業ディレクトリの隔離とは別に判断する。レビュー・再レビュー・再実行という理由だけで worktree を選ばず、その都度、別の変更状態を保持する必要があるか確認する。

子の worktree は親のコミットを起点とし、未コミットの変更は含まない。レビューや検証に必要な変更が揃うかを委譲前に確認する。また、worktree を分けても外部サービス・データベース・共有キャッシュなどは隔離されないため、それらの競合は別途避ける。

## 依頼と結果の確認

- 委譲の要否と目的 → 観点の分散なら provider → 委譲先のモデル × 思考レベルの順に決める。
- 依頼文に目的、必要な事実、対象範囲、変更可否、完了条件、報告形式を含める。子は会話履歴を持たない前提で書く。観点の分散が目的なら、メインの結論や仮説を渡さない。
- 大量の調査は、役割や依存関係に沿った小さな担当範囲に分け、各範囲の完了条件と残りの対象を明示する。分割を対象の省略や暗黙の件数上限にしない。
- 子の完了は実行の終了であって依頼の完遂ではない。返された結果を完了条件と照合し、差分・テスト・出典は親が確認する。未完了なら残作業と停止理由を確認し、再依頼・再分割・ブロッカーの報告を選ぶ。

## モデル × 思考レベルを選ぶ

### 使用量の確認

委譲先を選ぶ前に、T3 Code が provider ごとに保存している使用量を確認する。

```bash
python3 -I -c 'import json,glob,os; [print(os.path.basename(p)[:-5], json.dumps(json.load(open(p)).get("usageLimits",{}).get("windows",[]),ensure_ascii=False)) for p in sorted(glob.glob(os.path.expanduser("~/.t3/caches/*.json")))]'
```

`usedPercent` が 100 に達し、`resetsAt` を過ぎていない枠がある provider は、以降のすべての選定で候補から外す。`label` に対象が書かれた枠（`Weekly · Fable`、`Claude & GPT (shared)` など）は、その対象だけを外す。T3 の内部キャッシュのため、ファイルや項目がなければ確認できないものとして扱い、候補から外さない。

### 文章作成・ドキュメント更新の優先方針

文章の新規作成、構成の整理、推敲、ドキュメント更新では、Antigravity の **Gemini 3.8 Flash を第一候補**にする。ユーザーが文章品質を Claude・GPT より高く評価しているためで、比較データの点数から導いた順位ではない。これらの点数だけを理由に文章作成の候補から外さない。

low / medium / high は、構成や論旨の判断量、資料の複雑さ、検証の難しさに応じて選ぶ。実装と文書更新が混在する場合も、文章部分を切り出して Gemini に任せる。依頼には読者、目的、文体、根拠となる仕様・コード・資料を渡し、親が事実・コマンド・仕様との整合を確認する。メインがすでに同モデルなら、文脈分離などの必要がない限り直接書いてよい。

### 共通の選定手順

ユーザーの優先事項や指定があればそれに従う。

1. **作業の種類から指標を決める。** 各指標の意味・値・ぶれ幅は [model-benchmarks.md](model-benchmarks.md) を読む。
   - リポジトリの変更: FrontierCode
   - コマンド実行・環境の操作: Terminal-Bench
   - 揃った資料の読解・抽出・統合: GDP.pdf
   - 外部サービスをツール・API で操作する作業: 作業に含まれる変更・コマンド実行・読解に近い上の指標で帯を判定し、AutomationBench を候補間の比較の補助にする。
   - 大量のファイル・資料を探索して成果物にまとめる調査: 同様に上の指標で帯を判定し、AA-Briefcase を候補間の比較の補助にする。
   - 複数に当てはまる作業は、該当する指標すべてで帯の下限を満たす組み合わせから選ぶ。
   - コードレビューの見逃し・誤検出を直接測る指標はない。指摘の正否を確かめるのに必要な作業（コードの変更・コマンド実行）に近い指標を使う。
   - Intelligence・Omniscience は補助にとどめる。
2. **帯を決める。** 委譲前に次の 4 つに答える。

   | 問い | Yes の条件 |
   |---|---|
   | 1. 方針 | 何をどう変えるか、何を調べるかを、依頼文に手順として書ける |
   | 2. 範囲 | 結果に影響する箇所が、1 つのモジュール・設定・資料の中で閉じている |
   | 3. 検証 | 子の結果の正否を、親がテスト・差分・出典で短時間に判定できる |
   | 4. 影響 | 失敗してもやり直せば済む。外部への公開、データの破壊、後工程の大きな手戻りがない |

   - **下位帯**: 4 つとも Yes。熟練者なら 15 分未満で済む仕事に相当する。
   - **中位帯**: 3 と 4 が Yes で、1 と 2 のどちらか一方が No。15 分〜1 時間程度の仕事に相当する。
   - **上位帯**: 1 と 2 がどちらも No、または 3 か 4 のどちらかが No。1 時間を超える仕事に相当する。

   3 か 4 が No なら上位帯にするのは、手順 5 の切り替えが、失敗に気づけてやり直しの損失が小さい場合にしか成り立たないため。1 に答えられず完了条件も書けない場合は、帯を決める前に親が調べるか、依頼を分割する。
3. **帯の下限を満たす組み合わせから選ぶ。** [model-benchmarks.md の帯ごとの目安](model-benchmarks.md#帯ごとの目安) で、手順 1 の指標の該当する帯から、費用・時間が小さいものを選ぶ。起動・文脈共有・親による検証の負担も含めて比べる。
   - ベンチマークの成功率を個別タスクの成功率や品質保証として扱わない。
   - 指標同士や費用・時間を足し合わせて独自の総合点にしない。
4. **provider・モデルが先に決まっている場合は、思考レベルを次の基準で選ぶ。** 文章作成の優先方針、観点の分散、ユーザーの指定でモデルを先に決めた場合に使う。Anthropic と OpenAI の公式の目安で共通する部分を、全 provider 共通の開始レベルにしている。

   | 開始レベル | 作業 |
   |---|---|
   | low | 範囲と手順が決まっていて、結果を機械的に確認できる短い作業 |
   | medium | 仕様が明確な実装・調査。迷った場合の既定値 |
   | high | 原因が分からない不具合、設計判断、複数の状態・契約を追う作業、長い作業 |
   | xhigh・max | 開始レベルにしない。次の調整で効果を確認できた場合だけ上げる |

   開始レベルを決めたら、手順 1 の指標で同じモデルの上下のレベルと比べる。1 段上げたときの伸びがぶれ幅を超えれば上げる候補にし、ぶれ幅以内なら上げない。開始レベルの値が上のレベルよりぶれ幅を超えて低ければ、上のレベルから始める。Gemini 3.8 Flash は low〜high だけを使う。
5. **足りなければ上へ切り替える。** 推論が浅ければ思考レベルを上げ、意味の取り違えや能力不足なら一つ上の帯からモデルを選び直す。情報不足は依頼を補い、時間超過はまず範囲・依存関係・ツール待ちを確認する。認証・権限・ツール障害をモデル変更で解決しようとしない。

### 指定方法

`target` の provider・モデル ID と、`options` に指定できるキー・値は実行時の `orchestrator_capabilities` を正とする。Codex・Claude は 2026-10-27、Antigravity は 2026-11-03 に確認した対応:

| モデル | `providerInstanceId` | `model` | 思考レベルの option |
|---|---|---|---|
| Luna / Sol / Astra / Terra | `codex` | `gpt-6-luna` / `gpt-6.1-sol` / `gpt-6-astra` / `gpt-6.1-terra` | `reasoningEffort` |
| Opus / Fable / Sonnet / Haiku | `claudeAgent` | `claude-opus-5-5` / `claude-fable-5-1` / `claude-sonnet-5-5` / `claude-haiku-5-5` | `effort` |
| Gemini 3.8 Flash | `antigravity` | `gemini-3.8-flash` | `thinking_level`（low / medium / high） |

```json
{ "providerInstanceId": "codex", "model": "gpt-6.1-sol", "options": { "reasoningEffort": "high" } }
```

```json
{ "providerInstanceId": "antigravity", "model": "gemini-3.8-flash", "options": { "thinking_level": "medium" } }
```

- 思考レベルは原則として明示する。省略は親と同じ provider・モデルの設定を継承する意図がある場合に限る。
- 選んだ思考レベルを内蔵機能で指定できない場合は、T3 の指示どおり `delegate_task` を使う。
- 速度系の option（`serviceTier`、`fastMode`）はユーザーの指示がある場合だけ指定する。
- 比較データにない思考レベル（Codex の `ultra`、Claude の `ultracode` / `ultrathink` など）は根拠がないため、ユーザーの指示がある場合だけ使う。
