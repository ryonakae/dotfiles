# サブエージェントへの委譲

## 委譲するか決める

次のいずれかに当てはまれば委譲する。

- **並列化**: 互いに依存しない、それぞれまとまった量の作業が複数ある。
- **観点の分散**: 自分の変更のレビュー、複数案からの設計判断、原因を絞り込めない不具合の仮説検証で、メインの見方に引きずられない評価がほしい。数行の自明な変更は除く。目的に応じて provider を選ぶ。
  - モデル固有の偏りを補う: メインと別の provider（Claude と Codex）
  - 会話の文脈だけを切り離す、同じモデルでも同じ結論になるか確かめる: メインと同じ provider
  - 判断の影響が大きい: 両方に同じ依頼を出し、結果を比べる

次は、期待する利益が起動・文脈共有・結果待ち・親による検証の負担を上回る場合に委譲する。

- **速度・費用**: 範囲と報告形式を限定した調査などを、必要な品質を保ちつつ、メインより高速・低コストなモデル × 思考レベルで処理できる。
- **品質向上**: 難しい判断や重要なレビューを、そのタスクでメインより高い品質を見込めるモデル × 思考レベルに任せる。

## 依頼と結果の確認

- 委譲の要否と目的 → 観点の分散なら provider → 委譲先のモデル × 思考レベルの順に決める。
- 依頼文に目的、必要な事実、対象範囲、変更可否、完了条件、報告形式を含める。子は会話履歴を持たない前提で書く。観点の分散が目的なら、メインの結論や仮説を渡さない。
- 大量の調査は、役割や依存関係に沿った小さな担当範囲に分け、各範囲の完了条件と残りの対象を明示する。分割を対象の省略や暗黙の件数上限にしない。
- 子の完了は実行の終了であって依頼の完遂ではない。返された結果を完了条件と照合し、差分・テスト・出典は親が確認する。未完了なら残作業と停止理由を確認し、再依頼・再分割・ブロッカーの報告を選ぶ。

## モデル × 思考レベルを選ぶ

1. **タスクを評価する。** 必要な判断の量（固定手順か、解釈・設計か）、依存の広さ（局所か、複数の状態・契約を追うか）、正否の検証しやすさ、失敗時の影響を確認する。ファイル数や依頼文の長さだけで難易度を決めない。
2. **モデル × 思考レベルを一体で比較する。** 各指標の意味と値は [model-benchmarks.md](model-benchmarks.md) を読む。下位モデルの高い思考レベルと上位モデルの低い思考レベルも同じ候補に入れる。観点の分散で provider を決めた場合を除き、provider・モデルを先に固定せず、軽量作業では Luna・Terra・Haiku も候補に含め、上位モデルや高い思考レベルを自動的に選ばない。
3. **委譲内容とベンチマークの類似性を確認する。**
   - **実装・修正・検証まで任せる仕事**: Terminal-Bench を優先し、Intelligence を補助にする。
   - **入力資料が揃った読解・抽出・統合**: AA-LCR を参照する。知識に基づく回答では Omniscience も参考にする。Terminal-Bench の低さだけで候補を除外しない。
   - **探索を伴う調査**: 資料の発見、ツール操作、依存関係の追跡、仮説検証が必要なら AA-LCR だけで選ばない。探索経路の判断量と検証の難しさを評価し、ターミナル作業を伴う場合は Terminal-Bench も補助にする。
   - **コードレビュー**: 4 指標とも見逃し・誤検出を直接測らない。局所的で指摘をテスト等で確認できる仕事では軽量な候補も検討する。複数の状態・契約を追う仕事や、指摘・見逃しを検証しにくい仕事では、その推論を担える能力を優先する。「重要なレビュー」というだけで上位モデル・最大の思考レベルに固定しない。
   - **共通**: 費用・時間と思考レベルを変えたときの差を見る。高い思考レベルほど高得点になるとは限らない。小差だけで優劣を断定せず、ベンチマークの成功率を個別タスクの成功率や品質保証として扱わない。
4. **品質・時間・費用の釣り合う組み合わせを選ぶ。** ユーザーの優先事項に従い、指定がなければ次の順に判断する。
   - タスクの難しさ・検証可能性・失敗時の影響から、必要な品質を見込める組み合わせに候補を絞る。役割ごとの固定モデルや点数の閾値は設けない。
   - 残った候補間で、品質差を重視する根拠が弱い場合は費用・時間を比較する。起動・文脈共有・再試行・親の検証の負担も含める。
   - 品質の見込みに不確実性が大きく、失敗の影響も大きい場合は、費用・時間よりそのタスクに必要な能力を優先する。
   - 指標同士や費用・時間を足し合わせて独自の総合点にしない。
5. **不十分な結果は原因を切り分ける。** 推論が浅ければ思考レベル、意味の取り違えならモデルを再検討する。情報不足は依頼を補い、時間超過はまず範囲・依存関係・ツール待ちを確認する。認証・権限・ツール障害をモデル変更で解決しようとしない。

### 指定方法

`target` の provider・モデル ID と、`options` に指定できるキー・値は実行時の `orchestrator_capabilities` を正とする。2026-10-27 時点の対応:

| モデル | `providerInstanceId` | `model` | 思考レベルの option |
|---|---|---|---|
| Luna / Sol / Astra / Terra | `codex` | `gpt-6-luna` / `gpt-6.1-sol` / `gpt-6-astra` / `gpt-6.1-terra` | `reasoningEffort` |
| Opus / Fable / Sonnet / Haiku | `claudeAgent` | `claude-opus-5-5` / `claude-fable-5-1` / `claude-sonnet-5-5` / `claude-haiku-5-5` | `effort` |

```json
{ "providerInstanceId": "codex", "model": "gpt-6.1-sol", "options": { "reasoningEffort": "high" } }
```

- 思考レベルは原則として明示する。省略は親と同じ provider・モデルの設定を継承する意図がある場合に限る。
- 選んだ思考レベルを内蔵機能で指定できない場合は、T3 の指示どおり `delegate_task` を使う。
- 速度系の option（`serviceTier`、`fastMode`）はユーザーの指示がある場合だけ指定する。
- 比較データにない思考レベル（Codex の `ultra`、Claude の `ultracode` / `ultrathink` など）は根拠がないため、ユーザーの指示がある場合だけ使う。
