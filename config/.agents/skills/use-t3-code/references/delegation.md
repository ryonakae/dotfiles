# サブエージェントへの委譲

内容: 委譲の判断（ハイブリッド方針）、作業ディレクトリの共有・隔離、依頼と結果の確認、モデル・思考レベルの選定、読者向け文章の優先方針、プロバイダ固有の運用制約。

## 委譲を判断する（ハイブリッド方針）

原則として、現在起動中の親モデルで作業を完結させる。小〜中規模の実装・修正・局所確認は、依頼文作成や子の初期読込（コールドスタート）の負荷が利益を上回るため、親が直接処理する。

次の発動条件のいずれかに当てはまる場合だけサブエージェントへ委譲する。

- **独立レビュー**: 自分の変更や設計案に対して、実装時の思い込みを切り離した評価が必要なとき。レビュー要否の正本は `plan`・`implement` とし、それらを使わない通常作業では数行を超える差分の完了報告前を対象にする。観点の分散の目的に応じて系統を選ぶ。
  - モデル固有の偏りを補う: 親と別の系統（Claude・GPT・Gemini）を使う provider
  - 会話の文脈だけを切り離す、同じ系統でも同じ結論になるか確かめる: 親と同じ系統でも可
  - 判断の影響が大きい: 異なる系統に同じ依頼を出して結果を比べる
- **コンテクスト保護・並列化**: 読む対象を事前に特定できない横断探索や、互いに依存しないまとまった並列作業を、親のコンテクスト肥大・劣化を防ぎながら進める。
- **局所難所への上方委譲**: 親が最上位ティアでない場合に、依頼文へ切り出せる難所（原因調査、設計案の検証、局所的な難実装）を上位ティアへ任せる。作業全体が難所（方針・範囲ともに未確定）の場合は、ハンドオフ負荷が最大になるため子へ投げず、ユーザーへ親モデルの切り替えを提案する。
- **速度・費用・枠節約**: 範囲と手順を依頼文に書け、結果を機械的に確かめられる探索・確認（複数ファイル横断、ログ・テスト結果の確認、仕様や資料の抽出）を、軽量ティアへ任せて親の使用量枠と時間を節約する。対象と読む箇所が分かっていて数回のツール呼び出しで済む場合は直接処理する。
- **読者向けの文章**: 親が [models.md の文章スロット](models.md#文章スロット) と異なる系統の場合に、文言案の作成・推敲を委譲する。誤字・数値・リンクの機械的な修正だけなら直接処理してよい。

## 作業ディレクトリの共有・隔離を決める

子タスクは原則として親の作業ディレクトリを共有する（`shared`）。複数の変更状態を同時に保持する必要があるときに `worktree` を選ぶ。委譲前に、親と他の子タスクの編集・検証への干渉を確認する。

- **worktree が必要になる場合**: 相互に干渉する並列編集、異なる実装案をそれぞれ保持して比較する試作、親が編集を続ける間の固定コミットの検証、子ごとに独立したブランチ・PR を作る作業。
- **shared で進める場合**: 読むだけの調査、親が対象の編集を止めている間のレビュー、順番に行う修正。担当ファイルが別でも、依存関係や生成物・ビルド出力の競合を確認する。出力先の分離や実行順の調整で干渉を避けられるなら、新しい worktree は作らない。

レビューの独立性は作業ディレクトリの隔離とは別に判断する。レビュー・再レビュー・再実行という理由だけで worktree を選ばず、その都度、別の変更状態を保持する必要があるか確認する。

子の worktree は親のコミットを起点とし、未コミットの変更は含まない。レビューや検証に必要な変更が揃うかを委譲前に確認する。また、worktree を分けても外部サービス・データベース・共有キャッシュなどは隔離されないため、それらの競合は別途避ける。

## 依頼と結果の確認

- 委譲の要否と目的 → 系統（別系統が必要か） → ティア・思考レベルの順に決める。
- 依頼文に目的、必要な事実、対象範囲、変更可否、完了条件、報告形式を含める。子は会話履歴を持たない前提で書く。観点の分散が目的なら、メインの結論や仮説を渡さない。
- 大量の調査は、役割や依存関係に沿った小さな担当範囲に分け、各範囲の完了条件と残りの対象を明示する。分割を対象の省略や暗黙の件数上限にしない。
- 子の完了は実行の終了であって依頼の完遂ではない。返された結果を完了条件と照合し、差分・テスト・出典は親が確認する。未完了なら残作業と停止理由を確認し、再依頼・再分割・ブロッカーの報告を選ぶ。

## モデル・思考レベルを選ぶ

委譲すると決めたら、親と同一モデルに固定・制限せず、[models.md](models.md) のモデル表からティア・用途・別系統（およびプロバイダ別の使用量枠分散）に合うモデルを選ぶ。

### 1. ティアを決める

発動条件でティアやスロットが直接決まっている場合は、それに従う。

- **速度・費用・枠節約** → **軽量ティア**
- **局所難所への上方委譲** → **最上位ティア**
- **読者向けの文章** → [models.md の文章スロット](models.md#文章スロット)

それ以外の委譲（独立レビュー、コンテクスト保護・並列化など）でティアを決めるときは、委譲前に次の 4 つに答える。

| 問い | Yes の条件 |
|---|---|
| 1. 方針 | 何をどう変えるか、何を調べるかを、依頼文に手順として書ける |
| 2. 範囲 | 結果に影響する箇所が、1 つのモジュール・設定・資料の中で閉じている |
| 3. 検証 | 子の結果の正否を、親がテスト・差分・出典で判定できる。判定にやり直す以上の手間がかからない |
| 4. 影響 | 子が外部への公開・送信、データの削除など取り消せない操作をしない |

- **単純（4 つとも Yes）** → **軽量ティア**
- **困難（1 と 2 がどちらも No、かつ 3 か 4 も No）** → 依頼文に切り出せる局所難所なら **最上位ティア**。1 に答えられず完了条件も書けない場合は、親が先に調べるか分割し、作業全体が難所なら親モデルの切り替えをユーザーへ提案する。
- **通常（それ以外）** → **標準ティア**

親自身のティアは [models.md](models.md) で確認する。親がすでに最上位ティアの場合、上方委譲は発生しない。

### 2. モデル表から選定し、実行方法を決める

1. 決めたティアと系統の要件（別系統・使用量枠分散・文章スロット）に合うモデルを [models.md](models.md) から選ぶ。
2. 思考レベル（effort）の開始指針は次を目安にし、モデルの既定・引き上げ先・打ち止めは [models.md](models.md) に従う。

   | 開始レベル | 作業 |
   |---|---|
   | `low` | 範囲と手順が決まっていて、結果を機械的に確認できる短い作業 |
   | `medium` | 仕様が明確な実装・調査。迷った場合の既定値 |
   | `high` | 原因が分からない不具合、設計判断、複数の状態・契約を追う作業、長い作業 |
   | `xhigh`・`max` | 開始レベルにしない。不足時の引き上げ先として `models.md` に記載がある場合だけ使う |

3. 選定の結果、**親と同一プロバイダ・同一モデル・同一オプション**になった場合だけ内蔵サブエージェントを使う。それ以外は `delegate_task` で `providerInstanceId`・`model`・`options` を明示指定する。
4. **失効検知**: `orchestrator_capabilities` の出力で、`models.md` に記載した `model` ID が利用不能（消失）になっている場合は、無断で別モデルへ切り替えず [models.md](models.md) の更新を提案する。
   - **必須の独立レビュー**（`implement` 等、実装を担当していない read-only コンテクストを契約とするレビュー）は親が代行せず、利用可能な別モデルまたは親と同一モデルの独立コンテクストへ委譲するか、ユーザーへ確認する。
   - それ以外の委譲は、親が実施するかユーザーへ確認する。

### 3. 不足時の引き上げ

推論が浅ければ `models.md` の引き上げ先へ思考レベルを上げ、意味の取り違えや能力不足なら一つ上のティアからモデルを選び直す。情報不足は依頼を補い、時間超過はまず範囲・依存関係・ツール待ちを確認する。認証・権限・ツール障害をモデル変更で解決しようとしない。

## 読者向けの文章の優先方針

読者向けの文章の新規作成、構成の整理、推敲では、[models.md の文章スロット](models.md#文章スロット) を使う。ユーザーの明示指定がある場合はそちらを優先する。

- **対象**: README、ユーザー向けドキュメント、Web ページのコピー・記事、アプリの UI テキストのように、人間の読者がそのまま読む文章に限る。
- **対象外**: エージェント向けの指示・スキル、計画・仕様・設計記録、コードコメント、コミットメッセージ・PR 本文、チャットの回答。対象か迷う場合も対象外とする。
- **親が同系統のとき**: 親がすでに文章スロットと同じ系統なら、文脈分離の必要がない限り委譲せず直接執筆する。
- **別プロバイダから委譲するとき**: 担当は文言案の作成と親への返却に限定する。依頼文にファイル編集・シェルコマンド実行を行わない旨と、読者、目的、文体、根拠となる仕様・コード・資料の必要箇所を添え、返答には対象箇所と文言案だけを求める。親が事実・コマンド・仕様との整合を確認し、採用する文言を対象ファイルへ反映する。

## プロバイダ固有の運用制約

- **Antigravity**: `auto` でもシェルコマンドやワークスペース外のファイル読み取りで頻繁に承認を求めるため、委譲時は次のどちらかで運用する。指定できる `runtimeMode` は、親の権限（親が `auto` のときは子を `full-access` にできない）と `orchestrator_capabilities` の `runtimeModes` に従う。
  - **親が `full-access` で編集やシェル実行を明示委譲する場合**: `runtimeMode: "full-access"` を指定し、編集結果は親が差分を確認する。
  - **親が `auto` 以下、または編集させない作業（文章スロットの文言案作成など）**: `runtimeMode: "approval-required"`（既定）または `"auto-accept-edits"` を指定し、ファイル読み取りと案・分析の返却だけに限定する。ファイル編集は親エージェントが担当する。
