# Writing Plans

## 目的

セッションで確認した要件、決定事項、制約を、実装中に参照できる計画書として保存する。
計画書は次の役割を持つ。

- 決定事項や対象外事項の抜け漏れを防ぐ。
- 要件、実装タスク、検証方法の対応を明確にする。
- 実装の順序と現在の進捗を示す。
- 実装方法を必要以上に固定せず、完了条件を共有する。

計画書は実装コードの下書きではない。何を、なぜ、どの条件で実現するかを固定し、コード本文は実装時に既存コードへ合わせて書く。

## Plan-only のルール

このスキルを使うターンでは計画だけを作る。

- 実装コード、設定、テスト、ドキュメント本文は編集しない。
- 編集してよいのは計画ファイルだけ。
- 調査に必要な read-only 操作、検索、テストコマンドの確認はしてよい。
- mutating command、commit、push、外部サービスの変更操作はしない。
- 計画の成否に関わる未確定点がある場合だけ、短く確認する。
- 公開挙動、API・CLI 契約、データ形式、永続性、並行性、エラー形式、時刻境界など、利用者から見える結果を変える未確定事項は仮定で埋めず、計画作成前に確認する。
- 確認は、後続の判断を左右する上流の論点から一度に一つだけ行い、推奨回答と理由を添える。
- Assumptions に置いてよいのは、外部挙動を変えず、実装時に容易に変更できる軽微な事項だけとする。
- 事実、仮定、未解決事項を区別して計画に記録する。

計画を保存した後、実装へ進むかはユーザーに確認する。

## 保存先

ユーザーが保存先を指定した場合は、そのパスを優先する。
指定がない場合は、作業中のリポジトリに次の形式で保存する。

```text
docs/plans/YYYY-MM-DD-<slug>.md
```

`<slug>` は計画対象を短く表す英数字とハイフンの名前にする。既存ファイルを上書きしない。
実装が完了し、Final Validation のすべての項目が成功したら、計画ファイルを同名のまま `docs/plans/archived/` へ移す。検証が未完了または失敗している計画は移さない。

## 作成手順

1. 会話、ユーザー要件、関連文書、既存コードを読み、決定済みの内容と制約を収集する。
2. 事実、決定事項、仮定、未解決事項を区別する。外部挙動や公開コントラクトを左右する未解決事項は、仮定へ落とさず計画へ進む前に確認する。
3. Problem、Goal、Out of Scope を定義し、要件と重要な決定事項へ ID を付ける。
4. 変更対象ファイルと責務を既存パターンに沿って整理する。
5. 外部挙動をどのテスト境界で検証するか決め、入力、境界条件、期待結果を記録する。
6. 作業を、独立してレビューと検証ができる成果物単位のタスクへ分ける。
7. 各タスクへ対象要件、変更ファイル、実装上の制約、テストケース、完了条件、検証コマンドを書く。
8. Requirement Coverage で、すべての要件と重要な決定事項をタスクおよび検証へ対応付ける。
9. 計画を書き終えたら自己レビューし、仕様漏れ、対象外の混入、曖昧な完了条件、検証漏れを直す。
10. 複雑な計画、委譲前の計画、ユーザーがレビューを求めた計画では `references/plan-document-reviewer-prompt.md` を使って第三者レビューを依頼する。

## 計画書の構成

不要な項目は短くしてよい。ただし、決定事項、対象外事項、完了条件、要件カバレッジは省略しない。

````markdown
# [Feature or Change Name] Implementation Plan

> **For implementers:** Execute tasks in order unless dependencies allow otherwise. Mark a task complete only after its validation succeeds. Reflect minor implementation differences in the relevant task. Ask the user before changing requirements, Out of Scope, or public contracts.

## Problem Statement

[誰が何に困っていて、なぜ変更が必要か]

## Goal

[今回達成する状態]

## Out of Scope

- [明示的に対応しないこと]

## Requirements and Decisions

### Requirements

- **R1:** [必要な振る舞い、制約、互換性条件]
- **R2:** [境界条件や negative requirement]

### Implementation Decisions

- **D1:** [採用した方針と理由]
- **D2:** [重要なトレードオフや採用しなかった方針]

### Contracts

- [公開インターフェース、型、データ形式、不変条件]
- [必要なら短い signature、schema、状態遷移]

## Current Context

### Confirmed

- [確認した既存コード、仕様、運用上の事実]

### Assumptions

- [外部挙動を変えず、実装時に容易に変更できる軽微な仮定。なければ「なし」]

## File Structure

- Create: `exact/path/to/new_file.ext` — [責務]
- Modify: `exact/path/to/existing_file.ext` — [変更目的]
- Test: `exact/path/to/test_file.ext` — [検証対象]

## Testing Decisions

- **Test seam:** [どの外部境界から検証するか]
- **Behavior:** [主な入力、操作、期待結果]
- **Prior art:** [参考にする既存テストやパターン]
- **Avoid:** [内部実装への過剰な依存など]

## Progress

- [ ] Task 1: [レビュー可能な成果物]

実装中に判明した軽微なファイル変更や実装上の差異は、該当タスクへ反映する。要件、Out of Scope、公開コントラクトを変える必要が生じた場合は、計画を変更する前にユーザーへ確認する。

## Tasks

### Task 1: [Descriptive Name]

**Covers:** R1, R2, D1

**Objective:** [このタスクで達成する観測可能な状態]

**Files:**
- Create: `exact/path/to/file.ext`
- Modify: `exact/path/to/existing.ext`
- Test: `exact/path/to/test.ext`

**Dependencies:** [先行タスクや既存インターフェース。なければ「なし」]

**Implementation notes:**
- [守るべきコントラクトや既存パターン]
- [非自明なアルゴリズム、互換性、失敗時の扱い]
- [実装方法を不必要に固定しない]

**Test cases:**
- [入力・操作] → [期待結果]
- [境界条件] → [期待結果]

**Complete when:**
- [観測可能な完了条件]
- [回帰させてはいけない既存挙動]
- [記載した検証が成功すること]

**Validation:**
- Run: `[exact command]`
- Expected: `[期待する結果]`

## Requirement Coverage

| Requirement / Decision | Task | Verification |
|---|---|---|
| R1 | Task 1 | [テストケースまたは確認方法] |
| R2 | Task 1 | [テストケースまたは確認方法] |
| D1 | Task 1 | [設計上の制約を確認する方法] |

## Final Validation

適用する検証ごとに正確なコマンドと期待結果を書く。標準的な検証を適用できない場合は、`N/A` と理由を書く。

- [ ] `[focused test command]` — Expected: [期待する結果]
- [ ] `[relevant full test command]` — Expected: [期待する結果]
- [ ] `[typecheck, lint, or equivalent command]` — Expected: [期待する結果]
- [ ] [必要な手動確認または `N/A` と理由]
- [ ] Requirement Coverage に未対応項目がない
- [ ] 計画と実際の変更内容が整合している
- [ ] 上記のすべてが成功した後、計画を同名のまま `docs/plans/archived/` へ移した

## Risks and Open Questions

- [実装時に注意するリスク]
- [残っている未解決事項。なければ「なし」]
````

## コードを記載する基準

コードブロックは、実装案ではなくコントラクトを文章より正確に表せる場合だけ使う。

記載してよいもの:

- 関数や型の signature
- API、DB、設定の schema
- 状態遷移やデータ形式
- 文章では曖昧になる短い入出力例

記載しないもの:

- 関数やクラスの完成した実装本文
- テストコード全文
- import、boilerplate、機械的な設定全文
- copy-pasteable な実装パッチ
- 実装時に既存コードへ合わせて決めるべき内部詳細

## ファイル構成の考え方

タスクを書く前に、ファイルの責務を決める。

- 既存コードの配置、命名、テスト構成に合わせる。
- 大きすぎるファイルへ無理に追記しない。変更対象がすでに肥大化しているなら、分割を計画に含める。
- 既存設計を無視した大規模な再編はしない。
- 技術レイヤーだけで分けず、変更理由と責務で分ける。
- 一緒に変わるものは近くに置く。
- 後続タスクが依存する公開インターフェースは、必要な範囲で名前、引数、戻り値、型を明示する。

## タスク分割と進捗管理

タスクは「レビューできる最小の成果物」にする。2〜5分単位の操作には分解しない。
セットアップ、設定、スキャフォールド、ドキュメント更新は、それ単体で意味が薄いなら、必要とするタスクへ含める。

各タスクは次を満たす。

- 目的が一文で言える。
- 対応する要件または決定事項が分かる。
- 変更ファイルとテスト対象が具体的に分かる。
- 実行前の依存関係と実行後の成果物が分かる。
- テストまたは確認手順で完了を判定できる。
- コードを書き終えた時点ではなく、記載した検証が成功した時点で完了になる。

実装中は計画を現在の状態に保つ。

- タスクの Validation が成功したら、Progress の対応項目を完了にする。
- 実装中に判明した軽微なファイル変更や実装上の差異は、該当タスクへ反映して続行する。
- 要件、Out of Scope、公開コントラクトを変える必要が生じた場合は、計画を勝手に書き換えて進めずユーザーへ確認する。
- 実装後に計画と実際の変更内容が食い違ったまま残らないよう、Final Validation で確認する。
- Final Validation のすべてが成功してから、完了した計画を同名のまま `docs/plans/archived/` へ移す。

## 書かないもの

次の表現は計画の失敗として扱い、保存前に直す。

- `TBD`, `TODO`, `後で`, `適宜`, `必要に応じて` だけで中身がない記述
- 「バリデーションを追加する」「エラーハンドリングする」だけで条件や期待動作がない記述
- 「テストを書く」だけでテストケース、入力、期待値がない記述
- 「Task N と同様」だけで必要な差分が分からない記述
- 要件や決定事項と対応しないタスク
- 完了条件や検証方法がないタスク
- 未定義の関数、型、設定名、ファイル名への参照
- 実行コマンドだけで期待結果がない検証手順
- 会話や要件にない実装判断を、確定事項として追加する記述

## 自己レビュー

計画を保存する前に、次を確認して直す。

1. **決定事項の保持:** セッションで確定した振る舞い、制約、境界条件、対象外事項が記録されているか。
2. **要件カバレッジ:** 各要件と重要な決定事項に、対応タスクと検証方法があるか。
3. **スコープ:** Out of Scope が明示され、要件外の再設計や将来用の抽象化が混ざっていないか。
4. **コントラクト:** 公開インターフェース、型、データ形式、不変条件が必要な範囲で明確か。
5. **テスト可能性:** 外部挙動、入力、境界条件、期待結果、実行コマンドが具体的か。
6. **タスクの完了条件:** 各タスクが成果物単位で、検証後に完了を判断できるか。
7. **実装余地:** コード本文を先回りして固定せず、実装者が既存コードへ合わせられる余地があるか。
8. **事実と仮定:** 確認済みの事実、計画上の仮定、未解決事項が混同されていないか。
9. **仮定の境界:** 公開挙動、契約、データ形式、永続性、並行性、エラー形式、時刻境界に関する未確定事項を Assumptions で補っていないか。
10. **進捗管理:** Progress と Final Validation が、実装中に更新できる粒度になっているか。
11. **アーカイブ:** すべての Final Validation 成功後に、計画を同名のまま `docs/plans/archived/` へ移す指示があるか。

保存後は、保存パスと計画の要点だけを短く伝える。
