# Plan

合意した要件を、実装者が迷わず着手し、完了を判断できる計画へまとめる。
調査、記述、検証は、仕様の取り違えや手戻りを防ぐために必要な範囲に絞る。短くするために要件を落としたり、リスクのある境界条件を省いたりしない。

## Plan-only と保存先

- 編集してよいのは計画ファイルだけ。調査は read-only とし、実装、テスト実行、commit、push、外部サービスの変更はしない。
- 保存先はユーザー指定を優先し、指定がなければ `docs/plans/YYYY-MM-DD-<slug>.md`。既存ファイルを上書きしない。
- 計画を保存したら、パスと要点を短く伝え、実装へ進むか確認する。このターンでは実装しない。

## 調査と判断

1. 会話の合意、対象ファイルの指示、関連コードと既存テストを確認する。変更する処理の呼び出し元、公開契約、利用できる検証コマンドを、影響範囲が分かるところまで追う。
2. 要件、変更箇所、採用する既存パターン、完了の確認方法が分かれば計画を書く。関係のない領域の調査や、採用方針が明らかな場面での代替案比較は増やさない。
3. 外部挙動、互換性、データ保全、安全性や作業範囲を左右する未確定事項は、既存仕様で解決できなければ保存前に確認する。上流の論点から一度に一つ、推奨案と理由を添える。可逆な内部詳細は実装時に決めてよい。

確認した事実と提案・仮定を区別する。未合意の公開仕様を確定事項として書かない。
ファイルの肥大化や設計上の好みだけを理由に、依頼外の分割、再設計、将来用の抽象化を追加しない。

## 計画の粒度

- 要件や重要な決定事項は一か所に書く。タスクや検証では必要な差分だけを記し、同じ説明を繰り返さない。
- タスクは成果物単位にする。小さな修正は一つでよい。調査、テスト作成、実装、commit を別タスクにしない。
- 各タスクには変更対象と目的を書く。依存関係や実装メモは、知らないと誤実装や手戻りになる点だけを補う。
- コード本文やテスト全文は書かない。公開契約を正確に伝えるための短い signature、schema、入出力例は使ってよい。
- 要件 ID、対応表、全体のファイル一覧、独立した進捗一覧は標準では作らない。多数の要件が複数タスクにまたがり、対応を追いにくい場合だけ追加する。

## 検証の選び方

検証ごとに「どの要件や回帰リスクを確認するか」を説明できるものを選ぶ。項目数を増やすことを品質の代わりにしない。

- **自動テスト:** 継続して守る振る舞い、公開契約、不変条件を、既存の適切な境界から検証する。バグ修正は再現ケースを押さえ、変更に関係する境界条件・失敗経路を選ぶ。既存テストで保証できる性質は重複して追加しない。
- **一度きりの確認:** 削除した関数・ファイル・古い文言が存在しないことや、置換作業の完了だけを証明するテストは作らない。差分レビューや対象を絞った検索で確認する。ただし廃止 API の応答、ログへの秘密情報の非出力、配布物の禁止ファイルなど、不在そのものが継続的な契約・安全要件ならテストする。
- **範囲:** 変更に近い検証を基本とする。共有処理への波及、統合時のリスク、プロジェクトの必須ルールがある場合は全体テスト、型検査、lint、build などを加える。全体テストが小さく安価なら、それを選んでもよい。手動確認は自動検証で押さえられない点に絞る。
- **方法:** 自動検証は既存の正確なコマンド、一度きりの確認は対象と手順を記す。どちらも期待結果を書く。適用外の検証欄や `N/A` 一覧は作らず、テスト基盤のない変更に基盤新設を持ち込まない。
- **重複:** 検証方法は一か所にまとめ、タスクから必要なら参照する。実行順序の都合で再実行するのは、後続の変更や環境変化が先の結果を無効にする場合、またはプロジェクトの必須ルールがある場合に限る。

実行不能な必須検証は省略せず、制約と解決すべき判断を記す。失敗や未実行を成功扱いせず、受入条件の変更はユーザーへ確認する。

## 計画書の基本構成

以下を出発点にする。小さな変更なら各節を数行に収める。
公開契約、移行手順、リスクなどの独立した節は、今回の判断に必要な場合だけ追加する。空の節や「なし」で埋める欄は作らない。

```markdown
# [変更名] Implementation Plan

## Requirements

[解決する問題と達成したい状態。合意済みの振る舞い、守る制約、明示された対象外を記す。]

## Implementation Decisions

[主要な変更方針と理由。実装者に委ねる内部詳細は列挙しない。]

## Tasks

- [ ] [成果物]: `path/to/file` を [変更目的] のために変更する。
  - [誤実装を防ぐために必要な依存関係や注意点があれば記す。]

## Final Validation

[以下の各確認をどのタスクの完了判定に使うか、対応が明らかでない場合だけ補う。]

- [ ] [確認する振る舞い・条件]: [既存のコマンドまたは具体的な確認手順] → [期待結果]
```

計画末尾に実装者向けの次の指示を添える。

> 各タスクは対応する検証が成功してから完了にする。実装中の軽微な差分と検証結果は該当箇所へ反映し、要件、対象外、公開契約の変更はユーザーへ確認する。最終確認では有効な検証結果を再利用し、計画と実際の変更が一致することを確認する。必要な検証と実装側の必須レビューが通ったら、計画を同名のまま `docs/plans/archived/` へ移す。

## 保存前の確認

自己レビューで次を確認し、問題のある箇所だけ直す。

- 合意した要件、制約、対象外が残り、未合意の仕様や不要な作業を加えていないか。
- 各要件を実現する変更と完了の確認方法が読み取れるか。表の有無は問わない。
- 変更に伴う主要な回帰リスクを押さえ、重複テストや作業完了だけを証明するテストを増やしていないか。
- 実装者が再調査しなくてよい具体性があり、同じ情報の繰り返しや不要な内部詳細を削れるか。

第三者レビューはユーザーが求めた場合、またはデータ損失、権限、並行性、複数コンポーネントの契約など、誤判断の影響が大きく自己レビューだけでは確信が持てない場合に行う。委譲するという理由だけでは追加しない。
その場合は `references/plan-document-reviewer-prompt.md` を使う。
