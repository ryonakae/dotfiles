# dig log: t3-worktree・t3-merge スキルの汎用化

## 目的・前提・制約
- c-41 の `c41-worktree`・`c41-merge`（T3 Code で worktree を作成し、PR・マージ・片付けまで行うフロー）を、どのリポジトリでも使える汎用スキルにする。
- 配置先は `config/.agents/skills/`。mise の glob で `~/.agents/skills/` と `~/.claude/skills/` へ自動リンクされ、名前の列挙は不要。
- 確認した事実
  - `t3_worktree_handoff` は、スレッドがすでに worktree を持つと失敗する。引数は `branch`（必須）・`baseRef`・`startFromOrigin`・`continuationPrompt`・`runSetupScript`。
  - T3 の `storageCleanup.worktreeOnMerge` が有効で、PR マージ時に worktree が削除される。c-41 はこのため、マージと TestFlight 配信の起動を1コマンドに連結している。
  - 既定ブランチはリポジトリごとに異なる（c-41・lx・mog-web・zerdr は `main`、mog-app・violet-app は `develop`、hermes-agent は `ryonakae`、dotfiles は `master`）。
  - dotfiles は master へ直接コミットし、PR ではなく他 PC への同期で運用している。
  - `commit-push` は commit・push の正本。`implement` は feature branch を作らず current branch へ push する。
  - T3 のプロジェクト設定は `scripts`（`runOnWorktreeCreate`・`runOnSettle` など）を持ち、`t3_project_read`・`t3_project_update` で読み書きできる。設定は T3 の state に保存され、Git 管理外でマシンごとに別。
  - 登録済みプロジェクト5件のうち、worktree 作成時のスクリプトを持つのは c-41 だけ（`tools/worktree/setup.py`）。mog-app・violet-app・mog-web・dotfiles は未登録。
  - c-41 の準備は4層（準備スクリプト `tools/worktree/setup.py`、コピー対象の宣言 `.worktreeinclude`、T3 プロジェクト設定への登録、AGENTS.md の記述）。スクリプトの内容は LFS 展開・秘密ファイルのコピー・依存の導入などリポジトリ固有で、汎用スキルから本体は提供できない。
- c-41 のスキルの内訳は、T3 Code 共通の手順が大半で、固有部分は worktree 準備コマンド、TestFlight 配信、Simulator 削除、PR 本文の雛形、用語、判断表の固有条件。

## 決定事項
- 汎用スキルは `t3-worktree`・`t3-merge` の独立2本にし、`use-t3-code` からリンクする。
  - 理由: `t3-merge` を独立させるなら、対になる `t3-worktree` も独立させた方が分かりやすい。
  - 出典: dig 開始前のユーザー発言
- worktree の作成は、理由・基点・ブランチ名を提示し、ユーザーの承認後に行う。
  - 出典: dig 開始前のユーザー発言
- worktree を作るまでもない作業では worktree を作らない。読取調査、質問への回答、軽微な修正は現在の場所で進める。
  - 出典: dig 開始前のユーザー発言
- 基点ブランチは固定せず、リポジトリの既定ブランチを検出する。
  - 理由: 既定ブランチがリポジトリごとに異なる。
  - 出典: dig 開始前の提案（異論なし）
- worktree の提案は全リポジトリで有効にする。無効化は T3 のプロジェクト設定 `defaultThreadEnvMode` で表す。`local` なら提案しない、未設定なら作業規模で判断する、`worktree` ならスレッドは最初から worktree にあるのでそのまま続ける。
  - 理由: 新規リポジトリでも設定なしに機能する。判定が設定値1つで済み、整備済みの判定と同じ `t3_project_read` の結果を使える。
  - 制約: 設定はマシンごと。dotfiles は実装時に現在の PC で `local` を設定し、別 PC は同期時に設定する。
  - 出典: Q1、Q4
- T3 Code やworktree の設定（準備スクリプトなど）が未整備のリポジトリでは、worktree 作成より先に、その整備を案内する。
  - 出典: Q1 の回答
- 整備済みかどうかは、T3 のプロジェクト設定（`runOnWorktreeCreate` のスクリプトの有無）で判定する。AGENTS.md の記述を解釈する方式や、固定見出し・専用ファイルを新設する方式は採らない。
  - 理由: リポジトリごとに記述が異なり、自由記述は確実に拾えない。規約を新設せず、既存の設定で判断したい。
  - 出典: Q2 とその再質問への回答
- 判定は worktree を作成する直前にだけ、2段階で行う。(1) `runOnWorktreeCreate` のスクリプトがあれば整備済み。(2) なければリポジトリ内の兆候（依存の lockfile、primary checkout に実在し動作に必要な Git 除外ファイル、`.gitattributes` の LFS 指定）を確認し、兆候がなければ準備不要としてそのまま作成、兆候があれば未整備とする。
  - 理由: 規約を増やさず、準備不要のリポジトリでは何も質問せずに進める。別 PC で T3 への登録だけが欠けた場合も、同じ判定で検出できる。
  - 出典: Q3 の前提として提示（異論なし）
- 未整備のときは整備を提案し、承認されたら同じスレッドの現在の場所で先に整備する（準備スクリプトの作成、既定ブランチへの commit・push、T3 のプロジェクト設定への登録）。その後で元の依頼の worktree を作成する。「今回は準備なしで進める」も選べる。整備時の既定ブランチへの直接 push は提案時に明示する。
  - 理由: worktree は `origin` の既定ブランチから作成されるため、準備スクリプトは既定ブランチへ push 済みでないと新しい worktree に存在しない。急ぎの依頼のため必須にはしない。
  - 出典: Q3
- 汎用の `t3-merge` は共通手順だけを持つ（ブランチの決定、`commit-push` での commit・push、PR の作成、マージ可否の確認とマージ、ローカルブランチの削除、`thread-lifecycle.md` に従う付随物の片付け、報告）。iOS など特定の種類のリポジトリに固有の内容（配信、Simulator）は書かない。
  - 理由: すべてのリポジトリが iOS 開発ではない。
  - 出典: Q5 への指摘
- マージ前後の固有処理（配信、デプロイ、タグ付けなど）は、リポジトリ側の AGENTS.md やスキルに書き、`t3-merge` はそれを優先する。`t3-merge` には「リポジトリの指示が段階を置換・追加する場合はそちらに従う」と書く。固有処理のないリポジトリは何も書かない。差込口の規約（決まった id のスクリプトなど）は設けない。
  - 理由: 固有処理は種類も条件もリポジトリごとに異なる。大半のリポジトリは記述なしで機能する。
  - 出典: Q5
- `t3-merge` に、T3 がマージ時に worktree を削除するため、マージ後に worktree 内で実行する処理はマージと同一コマンドに連結する、という注意を書く。
  - 出典: Q5
- `t3-merge` の既定は履歴と設定に追従する。
  - マージ方式: 基点ブランチの直近のマージ済み PR と同じ方式。履歴がなければ `--merge`。
  - PR の基点: worktree の作成元のブランチ（既定ブランチ）。`main` に固定しない。
  - タイトル: 直近のマージ済み PR の形式と言語に合わせる。履歴がなければ `commit-push` のコミットメッセージ規則と同じ。
  - 本文: PR テンプレートがあればそれ、なければ「変更」「確認」の2見出し。
  - リモートブランチ: GitHub の自動削除が無効なら、マージ後にそのスレッドの作業ブランチだけ削除する。既定ブランチや `develop` などの常設ブランチは削除しない。
  - 理由: リポジトリごとの記述なしに現状の運用と一致する。確認した5リポジトリはすべて merge commit、タイトル形式は混在、自動削除が有効なのは c-41 だけ。mog-app は `develop` から `main` へのリリース PR を持つ。
  - 出典: Q6
- GitHub のマージ時ブランチ自動削除が無効なリポジトリでは、有効化を提案する。設定の変更は承認後に行う。
  - 出典: Q6 の回答
- 作業場所の判断は現在の場所に倒す。
  - 現在の場所: 質問への回答、読取調査、レビュー、計測。誤字・リンク・設定値など内容と影響が明確で局所的な修正。判断に迷う中間の作業（1ファイルで完結する不具合修正、依存1件の更新、小さな UI 調整など）。
  - その依頼の場所を継続: 同じ依頼の続き、レビュー指摘の修正。
  - 新しい worktree を提案: dig・Plan に進む変更、複数の commit に分かれる規模の変更（機能追加、複数箇所にまたがる修正、整理、性能改善）、PR でのレビューや確認が要る変更。
  - 例外: 現在の場所に他の作業の未コミット変更がある、または他のスレッドが同じ checkout で作業中なら、規模にかかわらず提案する。
  - worktree 側へ倒したいリポジトリ（c-41 など）は、AGENTS.md やリポジトリのスキルに書けばその指示が優先される。
  - 理由: worktree の利点は並行作業の分離と PR 単位での確認・取り消し。それが不要な作業では準備の時間とマージの手間だけが残る。
  - 出典: Q7
- 作業場所の判断表は `use-t3-code` 本体に置く（「サブエージェントへの委譲の判断」と並ぶ節）。`t3-worktree` は worktree を提案すると判断した後の手順だけを持つ（現在地の確認、整備済みの判定、初期整備、提案の書式、handoff）。`use-t3-code` の資料の表に `t3-worktree`・`t3-merge` へのリンクを足す。`references/worktree.md` は内容を `t3-worktree` に移して削除し、参照を置き換える。
  - 理由: 大半の依頼は worktree を提案しないので、必ず読む `use-t3-code` で判断できれば追加の読み込みが要らない。基準を2箇所に書かずに済む。
  - 出典: Q8
- c-41 には dotfiles のグローバル設定への依存を持たせない。c-41 を別のマシンへ clone しただけの状態でも、作業場所とマージのフローが機能するようにする。c41-worktree・c41-merge は縮小せず、全文を持つ独立したスキルとして維持する。
  - 帰結: 共通手順は dotfiles と c-41 に重複する。リポジトリをまたぐ重複は許容する。
  - 帰結: 汎用スキル側に「リポジトリが作業場所・マージの手順を独自に持つ場合は、そちらを使い、汎用スキルは使わない」と書く（段階単位の上書きに加えて、全体の置換を認める）。独自の手順の形式は問わない（スキル、AGENTS.md の記述など）。
  - 出典: 終了確認への回答
- c-41 に現存するグローバルスキルへの参照3件は、スキル名・ファイル名の指定をやめ、行為だけを書く形にする（「commit して push する」「子スレッド・ブランチを片付ける」など）。グローバルのスキルがある PC ではエージェントがその手順に沿い、ない PC ではエージェントの判断で実行する。内容を c-41 へ書き写すことはしない。作業は c-41 の別スレッドで行う。
  - 理由: 名前で参照しなければ依存にならず、書き写しによる重複も生じない。
  - 出典: Q10 への回答
- ブランチ自動削除の有効化の提案は、初期整備の提案に含める。整備済みで無効のままなら、`t3-merge` の報告で1行添える。
- `t3-merge` はユーザーが commit・push、PR 作成、マージを明示的に頼んだときだけ使い、完了報告では提案しない。一部だけ頼まれたらその範囲で止める。
- チェックが待ち・実行中なら、マージせず `watch_pull_request` して手を返す。コンフリクト・チェックの失敗・レビューの要求があれば報告して止める。`--admin` や強制 push は使わない。
- `defaultThreadEnvMode` が `local` のリポジトリでも、PR・マージを明示的に頼まれたら `t3-merge` の手順で行う（既定ブランチにいれば作業ブランチを切る）。
- スレッドの settle と worktree の削除は `t3-merge` に含めず、T3 Code に任せる。
  - 出典: 上の5項目は終了確認で合意
- 他のリポジトリから汎用スキルを名前で参照させる設計は採らない。dotfiles 内のスキル同士（`t3-merge` から `commit-push` など）は名前で参照してよい。
  - 出典: Q10 の帰結として提示（異論なし）

## 対象外
- c-41 リポジトリの編集（別スレッドで行う）。
- 準備スクリプト本体の汎用提供（内容がリポジトリ固有のため、各リポジトリで作成する）。

## 撤回・置換済み
- Q2 の当初推奨「AGENTS.md の記述を正本にする」「固定見出しを置く」は撤回。T3 のプロジェクト設定での判定に置換。
- Q1 の「AGENTS.md に記述して無効化」は撤回。`defaultThreadEnvMode` での表現に置換（Q4）。
- Q9 の「c-41 側のスキルを差分だけに縮小する」は撤回。c-41 は独立した全文のスキルを維持する（グローバル設定に依存させない）。
