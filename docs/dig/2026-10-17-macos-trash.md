# dig log: rm 転送先を gtrash から macos-trash へ切り替える

## 目的・前提・制約
- 目的: Safehouse 内で実行される rm の転送先を、Finder のごみ箱 `~/.Trash` に入るツールへ変える。gtrash は `~/.local/share/Trash` に保存し、Finder に表示されないため使いづらい。
- 関連する既存決定: [Safehouse の互換性優先設定と削除事故対策](2026-10-02-safehouse-compatibility.md)。Safehouse 内だけで転送し、外では `/bin/rm` を使う。Safehouse 内の `/bin/rm` 実行拒否、ごみ箱内容の保護、コピー fallback なしを維持してきた。復元はユーザーが sandbox 外で行い、エージェントによる復元は要件に含めない。
- 確認済みの事実:
  - gtrash 0.0.6 は XDG 形式のごみ箱専用。作者は macOS のごみ箱に対応しない方針を示している（umlx5h/gtrash#4）。
  - macos-trash 3.1.0 は Homebrew 公式 formula で、keg-only（理由 `shadowed_by_macos`）。`FileManager.trashItem` で移動し、複数ファイル時に欠ける「戻す」記録を `.DS_Store` へ補う。`--empty` は Finder 経由でごみ箱を空にする。
  - macos-trash の引数処理（ソース読解、未実行）: 先頭に連続するオプションで動作を決める。パスはハイフンで始まるものをすべて除外し、先頭以外の `--` はパスとして扱う。`-v` と `-h` は表示だけで終わる。このため `rm -f -- x` は `--` という対象で失敗して終了コード 1、`rm -f 存在しない名前` も 1、ハイフンで始まる名前は何もせず 0 になる見込み。
  - Swift の `URL(filePath:)` は空文字と `.` を現在のディレクトリへ、`..` を親ディレクトリへ解決する（実測）。macos-trash に空文字や `.` を渡すと、現在のディレクトリをごみ箱へ移す見込み（推定、未実行）。現行の gtrash 転送は空文字やハイフンで始まる名前をエラーにしており、削除はしない。
  - macOS の `man rm`: `/`、`.`、`..` の削除はエラー。`-f` は存在しない対象について診断も終了コードの変更もしない。`-f` と `-i` は後に指定した方が優先される。`--` 以降はハイフンで始まる名前もファイルとして扱う。
  - 同じ API を使う macOS 標準の `/usr/bin/trash` は、Safehouse 内から `~/.Trash` へ移動できた（実測）。`HOME` を変えても実際の `~/.Trash` に入る（実測）。壊れた symlink も symlink のまま移動できた（実測）。標準 trash は `-rf` を拒否して終了コード 1（実測）。
  - Safehouse 内で初回に trash した時点で `~/.Trash/.DS_Store` が 0 バイトで作られた。現行 `local-overrides.sb` が `~/.Trash` 配下の内容の読み書きを拒否しており、「戻す」記録を書けなかったと推定（時刻とサイズからの推定）。
  - Safehouse の基本 policy は `(deny default)` で `appleevent-send` の許可がない。Finder 経由の操作は動かない見込み（未検証）。
  - 既存の gtrash ごみ箱に 84 件の項目がある（件数のみ確認、内容は未確認）。
  - ラッパーの役割: `~/.local/bin/rm` として配置され、fish と Safehouse の起動スクリプトの両方で PATH の先頭に置かれる。名前で呼ばれた rm は `/bin/rm` より先にラッパーへ解決される。Safehouse 内なら転送し、外なら `/bin/rm` をそのまま実行する。対象はエージェントに限らず、Safehouse 内で動く rm すべて。
  - `/bin/unlink` は `/bin/rm` と同じ実体だが、Safehouse の実行拒否は `/bin/rm` のパスだけが対象で、Safehouse 内から直接削除できた（実測）。rm 以外の削除手段を防がないことは前回の決定で受け入れ済み。
  - 現行 `scripts/tests/test_rm_trash.py` は偽の gtrash で、引数の保持、終了コード、gtrash 欠落時に実 rm へ fallback しないこと、fish と子シェルからの解決を確認している。`check_gtrash_runtime.py` と `check_safehouse_runtime.py` はダミー HOME 前提のため、実際の `~/.Trash` を使う macos-trash はそのままでは検証できない。`test_agent_runtime.py` にも、非対話の起動経路で rm がラッパーへ解決されることを偽の gtrash で確かめるテストが 1 つある。
  - リポジトリの CLAUDE.md と AGENTS.md は、起動ラッパーと setup 入口を変えたときに `scripts/tests/` の関連テストを実行するよう定めている。
- 制約:
  - Safehouse の policy 変更はセキュリティ設定の変更で、別途承認が要る。次回起動から反映される。
  - Homebrew 導入や mise apply などの実機適用は別承認。
- 調査時の副作用: `~/.Trash` に検証用の項目 6 件と 0 バイトの `.DS_Store` を作成した。ユーザーが sandbox 外で削除する。
  - `claude-trash-probe-20261017-130730-a.txt`、`-b.txt`、`-dir`、`claude-trash-probe-20261017-130744-c.txt`、`fake-home-probe.txt`、`claude-trash-probe-broken-link`
  - 0 バイトの `.DS_Store` は「戻す」の検証の前提を崩す。macos-trash は読み取りに失敗すると記録の補完を黙って飛ばすため、検証前にユーザーが sandbox 外で削除する必要がある。

## 決定事項
- rm の転送先を gtrash から macos-trash に切り替える。
  - 理由: rm のフラグを無視する置換用の設計で、「戻す」記録の欠落も補う。標準 trash は rm のフラグを拒否する。
  - 出典: 調査報告後のユーザーの「macos-trashにしてみよう」。
- rm の引数はラッパーで最小限に整形してから macos-trash へ渡す。
  - macos-trash には常に `--` を先頭に付け、対象だけを渡す。macos-trash は `--` の後でもハイフンで始まるパスを除外するため、そうした対象もハイフンで始まらない形に直して渡し、移せるようにする。
  - 空文字、`/`、`.`、`..` は rm と同じくエラーにして移さない。`.` と `..` は末尾のスラッシュを除いた最後の要素で判定する。
  - `-f` のときは存在しない対象を飛ばし、診断を出さず、終了コードにも反映しない。
  - 拒否や失敗があっても残りの対象は処理し、最後に非 0 で終了する。
  - 以前の「独自の rm 互換実装はしない」方針は、この最小整形に限って変更する。
  - 理由: そのまま渡すと、空文字や `.` で作業ディレクトリごと移る、`rm -f -- x` が失敗する、ハイフンで始まる名前を移さず成功扱いになる。今の gtrash 転送より危険になる。
  - 出典: Q1 へのユーザー回答「a」。
- `-i` または `-I` が指定されたら、エラーで終了し何も移さない。
  - 理由: 確認なしで移すのは危険で、確認モードへ渡すと `-f` との後勝ちや `-I` の条件の再現が必要になる。エージェントの実行環境では標準入力が閉じていることが多く、rm でも何も消えない。
  - 出典: Q2 へのユーザー回答「a」。
- macOS の rm が受け付けないオプションと `-W` は、エラーで終了し何も移さない。`-d`・`-f`・`-P`・`-R`・`-r`・`-v`・`-x` は受け付ける。
  - 理由: 実際の rm と同じ結果になる。`-W` は復元を試みるオプションで、無視して移すと意図と逆になる。GNU 形式の長いオプションや打ち間違いで予期しない移動を起こさない。
  - 出典: Q3 へのユーザー回答「a」。`-v` で名前を表示するかは計画で既定を決める。
- ディレクトリの扱いは rm と同じにする。`-r` か `-R` がなければエラーにして移さない。`-d` だけなら空のディレクトリに限って移し、空でなければエラーにする。ディレクトリを指す symlink はリンクとして移す。
  - 理由: エージェントが rm に期待する結果とそろい、`rm *` のような書き方でサブディレクトリまで移る事故を防ぐ。今の gtrash 転送はオプションに関係なくディレクトリを移しており、この点は挙動が変わる。
  - 出典: Q4 へのユーザー回答「b」。
- Safehouse から `~/.Trash/.DS_Store` に限って内容の読み書きを許可し、エージェントが消したファイルも Finder の「戻す」で戻せるようにする。ゴミ箱の中身の読み取り・書き換え・削除の拒否は維持する。
  - 許可で増えること: ゴミ箱にある項目の名前と元の場所を読める。「戻す」の記録を書き換えられ、悪意のある書き換えでは別の場所へ戻される可能性がある。
  - 並行実行時に「戻す」の記録が欠けることは既知の制限として受け入れる。macos-trash は記録をロックせずに読み書きする。ファイル自体はゴミ箱に入る。
  - ゴミ箱全体は許可しない。ゴミ箱への移動と一覧は今の設定でも拒否されておらず、Safehouse 内から移動できた（実測）。全体を許可すると、復旧先の中身を読まれたり完全に削除されたりする。
  - macos-trash が使う DSStore ライブラリは、一時ファイルを使わず `.DS_Store` へ直接書き込む（ソース確認）。標準 API 側の書き込み方法は未確認。実装中のセッションは旧設定のままで確かめられないため、導入時のユーザーの手動確認で判断する。
  - 理由: 目的は Finder から楽に戻せるようにすること。許可しないと元の場所が分からず、gtrash より戻しにくくなる。HOME の大半はすでに読めるため、増えるリスクは小さい。
  - 出典: Q5 へのユーザー回答「A」と、ゴミ箱全体の許可が要らないかという確認。
- 外部ボリュームのゴミ箱は今回の対応範囲に含めない。
  - Safehouse は外部ボリュームへ書き込めず、`/Volumes/External SSD` と SMB の `/Volumes/Downloads` で実測した。作業ディレクトリが外部ボリュームにあっても、移動先の `.Trashes/<uid>` に書けないため移動は失敗し、元のファイルは残る見込み。gtrash でも同じく失敗しており、挙動は変わらない。
  - 出典: 環境の確認。異論があれば見直す。
- 切り替えと同じ変更で、gtrash 用の保護ルール、Brewfile の gtrash、関連する検証を削除する。
  - gtrash 用の保護ルールは `local-overrides.sb` の正規表現の行。`~/.local/share/Trash/files` などの Linux 形式のごみ箱を対象にしている。`~/.Trash` の中身の保護は残す。
  - 出典: Q6 へのユーザー回答「aでいい」。
- gtrash 本体のアンインストール時に、`~/.local/share/Trash` をフォルダごと削除してよい。中身の確認や移行はしない。
  - Safehouse 内からは保護ルールで中身を消せず、`/bin/rm` も拒否されるため、Safehouse 外の通常端末で行う。新しい設定で Safehouse を起動する前に済ませ、保護のない期間を作らない。
  - gomi は導入されておらず、このフォルダを使うツールは gtrash だけ（確認済み）。
  - 出典: Q6 へのユーザー回答「gtrashのゴミ箱に入っているフォルダのこととか、もう無視でいいでしょ。gtrashをアンインストールするときに一緒にフォルダごと消してくれていい」。
- gtrash の実機検証スクリプトは削除し、macos-trash 用の実機検証スクリプトは作らない。rm 関連で残すのはラッパーの単体テストだけで、gtrash 前提の部分を書き換える。
  - `check_gtrash_runtime.py` は削除する。
  - `test_rm_trash.py` は偽の macos-trash を使う形に書き換え、Q1 から Q4 の引数整形を固定する。
  - `test_agent_runtime.py` の rm 解決のテストは、偽のバイナリを gtrash から macos-trash に差し替えるだけにする。非対話の起動経路で rm がラッパーへ解決されることを確かめるテストで、整形とは別に今も有効なため。
  - `check_safehouse_runtime.py` は、削除する gtrash 用の保護ルールに対応する項目だけを除く。`~/.Trash` の中身の保護、`/bin/rm` の実行拒否、そのほかの項目は触らない。`.DS_Store` 許可の確認項目は追加しない。
  - 導入時に一度だけ、Safehouse 内で rm したファイルを Finder で「戻す」できるか手動で確かめる。`.DS_Store` だけの許可で足りるかは推定のため。
  - リポジトリ全体のテスト方針と CLAUDE.md・AGENTS.md の検証ルールは今回変えない。
  - 理由: 引数整形の誤りは作業ディレクトリごと移す事故につながるため、単体テストで変更のたびに防ぐ。本物のゴミ箱に触れる実機検証は得るものが少ない。全体の方針変更は今回の切り替えと分ける。
  - 出典: Q7 へのユーザー回答「b」。その前に「検証とかいります？」「そもそも、dotfilesにテストとか不要なんですけど」との発言あり。
- 計画の既定として、適用の順序と細部を次のとおりにする。
  - 適用の順序: 設定ファイルは symlink で即時に反映され、Safehouse の設定は次回起動から反映される。
    1. 変更を `~/dotfiles` へ取り込む前に、ユーザーが通常端末で macos-trash を導入する。未導入のままラッパーが切り替わると、Safehouse 内の rm は何も消さずに失敗する。
    2. 実装では、Brewfile、ラッパー、Safehouse の設定、文書、テストを変更する。実装中の Safehouse は旧設定のままなので、移した項目に「戻す」の記録は付かない。
    3. 実装後に、ユーザーが Safehouse のセッションと Hermes のサービスをすべて止める。通常端末で gtrash をアンインストールし、`~/.local/share/Trash`、検証用の項目、0 バイトの `.DS_Store` を削除する。その後に再起動し、Safehouse 内で rm したファイルを Finder で「戻す」できるか確かめる。旧設定のセッションが残っていると、`.DS_Store` がない状態での rm が 0 バイトの `.DS_Store` を作り直すため、停止を先にする。
    4. 「戻す」が出ない場合は、Finder でゴミ箱を開く前に `~/.Trash/.DS_Store` のサイズを見る。0 バイトなら、標準 API が `.DS_Store` 以外にも書き込みを必要としている。Safehouse の設定の追加変更を別途検討する。
  - ラッパーと Safehouse の設定は、`~/dotfiles` 上で編集した瞬間に、実行中のすべての Safehouse セッションと Hermes のサービスへ反映される。書きかけのラッパーが空文字や `.` の拒否より先に転送すると、Q1 で防ぎたい事故が起きうる。実装は Worktrunk の worktree で行い、完成してから `~/dotfiles` へ取り込む。macos-trash の導入は取り込みより前に済ませる。
  - ラッパーは keg-only の macos-trash を `/opt/homebrew/opt/macos-trash/bin/trash` の絶対パスで実行する。見つからない場合も `/bin/rm` へ fallback しない。既存の決定を維持する。
  - `-v` は受け付けて何も表示しない。エラー時の終了コードは 1 にする。
  - 対象の指定がない場合、`-f` があれば何もせず 0 で終わり、なければ使い方を表示してエラーにする。`man rm` の `-f` の説明に合わせる。
  - `local-overrides.sb` の、rm を gtrash へ転送すると書いたコメントを macos-trash に直す。
  - トラブル対応の復元手順を、Finder の「戻す」に書き換える。通常端末でゴミ箱を使いたい場合は macOS 標準の `trash` を案内する。macos-trash の作者によると、標準 API は複数を一度に移すと一部の「戻す」記録が欠ける。
  - 2026-10-02 の dig log の gtrash 採用の節に、この dig log で置き換えたことを追記する。
  - 出典: 共通理解の確認に対するユーザーの「ok」。
