# dig log: Safehouseのファイル保護を維持した互換性優先設定

## 目的・前提・制約
- Claude Code、pi、Codex、OpenCode、Antigravity CLIをmacOSで共通のラッパーから起動し、設定をdotfilesで管理する。
- ユーザーはSafehouse利用時にツールが動かないなど、ファイル読み書き以外の制約による調整負担を減らしたい。
- ファイルアクセス制限の最優先目的は、AIによる `rm -rf` などの意図しない削除・データ喪失を防ぐこと。機密・私的ファイルの読み取り保護も重要だが、削除防止より優先度は低い。
  - 出典: Q2後のユーザー発言。Q3:AでSafehouseと通常のrmのごみ箱化を併用する方針に合意した。
- ユーザーはサブプロセス起動を原因と考えているが、具体的な故障経路は未特定。環境変数、IPC、プロセス制限、内蔵sandboxのネストを区別する。
- Safehouse、sbox、nono、srt、VM・コンテナ方式を調査済み。現在のMac上のツール連携を維持するため、Safehouse設定の見直しを選択した。
- インストール済みSafehouseは0.12.0。標準の環境継承方式は全継承または指定変数の継承であり、秘密以外を全継承する標準フラグは確認できない。
- 現在の共通fish引数は `config/.config/fish/functions/__safehouse_args.fish`、追加ポリシーは `config/.config/agent-safehouse/local-overrides.sb`。
- gateway/dashboardのラッパーは共通引数と原則同期する。ただし非対話サービスの既存の意図的差分を尊重する。
- 既存の他者変更 `config/.claude/settings.json` と `config/.pi/agent/settings.json` を保持する。
- 参照範囲は本会話と現在のリポジトリ・インストール済みSafehouse。別セッションの議論は推測しない。同テーマの既存dig logは見つからなかった。

## 決定事項
- 他製品へ移行せず、Safehouseの設定を見直す。
  - 理由: 既存のCLI・Mac固有ツールへの対応を維持して調整負担を減らす。
  - 出典: 開始前の発言「agent-safehouseの設定を見直す方向でいきますか」。
- 環境変数はフィルタせず、そのまま引き継ぐ。
  - 出典: Q1へのユーザー回答で前言撤回。「環境変数はそのまま渡っていい」。
  - 秘密の保管・注入にはdotenvxを採用する方針。suin/opx、1Password Environments、SOPSとの比較を経て、Q2:A・Q4:B・Q5:Aでdotenvxの利用方法に合意した。具体的な移行範囲は未確定。
  - dotenvxはGitへの登録なしでもローカルの暗号化・実行時注入に利用できる。Git管理の要否と鍵のバックアップは別の判断。
- アプリケーション用の秘密は、必要なコマンド単位でdotenvxから注入する。エージェント本体にプロジェクトの秘密をまとめて注入しない。エージェント自身の認証に必要な秘密は別扱い。
  - 出典: Q2:Aへのユーザー合意。「A」。
- グローバルに利用する秘密は、ツールごとに分割せず、共通の暗号化環境ファイル一つにまとめる。
  - 理由: 管理の手間を減らす。
  - 出典: Q4:Bへのユーザー合意。「面倒だからBにするのが現実的かな」。
  - 共通ファイルは `~/.config/.env` とする。プロジェクト用秘密のQ2:Aとは区別する。
- 共通の暗号化環境ファイルの配置先は `~/.config/.env` とする。
  - 出典: Q9の説明後のユーザー提案「`~/.config/.env` とかの方がよくないですか？」。
  - dotenvxには明示的なファイルパスを指定する。実ファイルの作成・既存秘密の移行はまだ行っていない。
- 共通の暗号化.envはGit管理せず、`config/.config/.env.example` を秘密を含まないテンプレートとしてGit管理する。
  - 出典: Q9:Aへのユーザー合意。「a。 .env.example を置く感じで」。
  - 実体は `config/.config/.env`（既存の `.gitignore` の `.env` により管理外）とし、`~/.config/.env` へsymlinkする。既存の `scripts/copy.sh` と `scripts/create-symlink.sh` の例ファイル運用に合わせる。
- Context7などのグローバルなツール用秘密は、dotenvxを使ってエージェント起動時に自動注入する。
  - 理由: ツールごとの設定やAIによる特別なコマンド選択に依存せず、既存の起動ラッパーへ集約する。
  - 出典: Q5:Aへのユーザー合意。「a」。
  - 注入した値はエージェント本体と環境を継承する子プロセスから利用できる。この露出を許容し、保管時の平文を減らす。
- ホストプロセス操作を許可してよい。
  - 出典: 開始前のユーザー指定。
- IPCおよびMacサービスとの通信を許可してよい。
  - 出典: 開始前のユーザー指定。
- GUI連携を許可してよい。
  - 出典: 開始前のユーザー指定。
- 機密・私的ファイルの読み取り保護は維持する。一方、書き込み範囲は現在の広い許可を維持し、さらに拡大してよい。
  - 理由: 作業外への書き込みを制限するより使い勝手を優先し、通常の削除事故はgomiで備える。
  - 出典: Q6:Bへのユーザー回答。「Bだし、もっと広げていい。そのためにgomi入れようとしてる」。
- HOME配下は原則読み書き可能にし、機密・私的ファイルなど保護を残す対象だけ明示的に拒否する。
  - 理由: パスごとの許可追加を減らす。
  - 出典: Q7:Aへのユーザー合意。「a」。
  - 既存の保護対象を単純なHOME許可で再開放しないよう、保護ルールを後段に適用する。
- Safehouseとgomiを併用する。通常の `rm` をgomiへ流して復元可能にし、Safehouseでは維持する読み取り保護と承認する範囲のファイル制限を適用する。
  - 出典: Q3:Aへのユーザー合意。Q6:Bで、作業リポジトリ中心に書き込みを絞る案は撤回した。
  - PATHラッパー、永久削除・ごみ箱掃除の扱いはまだ未確定。
- 通常のrmのごみ箱化は、エージェントだけでなく普段のターミナルにも適用する。
  - 理由: 実行場所ごとの使い分けを避ける。
  - 出典: Q8:Bへのユーザー合意。「使い分けがややこしいからb」。
  - OSの `/bin/rm` 自体は置き換えず、ユーザー環境のPATH上のrmラッパーを共通で利用する設計を検討する。
- dotenvxの復号鍵はmacOS Keychainに保存する。
  - 理由: 復号鍵を平文ファイルとして保管しない。
  - 出典: Q11:Aへのユーザー合意。「a」。
  - Hermesのlaunchd経由・非対話起動から鍵を取得できることを検証条件とする。取得できない場合は方針を再確認し、勝手に `.env.keys` へ切り替えない。
- Hermes gateway/dashboardにもHOMEの広い許可・gomi・dotenvxによる共通キーの自動注入を適用する。
  - 出典: Q10:Bへのユーザー合意。「b」。
  - 対話CLIと常駐サービスで共通方針を揃える。既存の非対話用途に意図したfeature差分は維持する。

## 対象外
- 今回のdig段階での設定本体の変更、インストール、commit、push。
- VM・コンテナへの移行。
- ファイル以外の制限を緩めた状態で、外部アプリ・MCP・Docker・Keychain経由まで含めた完全な隔離を保証すること。

## 未決・保留
- 採用するdotenvxのバージョンとKeychainによる非対話利用は実機確認が必要。以下は採用方針を決める際の比較資料で、実機検証はしていない。
  - dotenvx: `.env` の値を暗号化し、`run` で実行時に復号して注入する。現行公式サイトは開発用秘密鍵の標準保存先をOS secret storeとしている。今回の鍵保管方式はQ11:AでmacOS Keychainに決定済み。
  - suin/opx: `op run` の薄いラッパー。現在地から親ディレクトリへ最も近い `.env` を探す。ファイルには `op://` 参照を記述し、秘密の実体を1Passwordに保存する。暗号化ツールではない。明示パスで十分なら公式 `op run --env-file` で代替できる。
  - 1Password Environments: プロジェクトごとの変数を外部管理する。ローカル `.env` はFIFOで、平文をディスクへ保存しない。ただし解除中はプロセスを区別せず読め、同時アクセスやViteなどのファイル監視に制約がある。CLIからのEnvironment注入は取得時点の公式資料でbetaとされている。
  - SOPS: ENV/YAML/JSONなどを暗号化し、age/PGP/KMSなどで鍵管理する。`exec-env` でディスクへ平文を書かずに実行環境へ注入できる。秘密鍵の保管・バックアップ・アクセス制限が必要。macOSのage鍵の標準パスはXDG設定の有無で変わる。
  - 出典: https://dotenvx.com/ 、https://github.com/suin/opx 、https://www.1password.dev/environments/local-env-file 、https://www.1password.dev/environments/read-environment-variables 、https://www.1password.dev/cli/reference/commands/run 、https://getsops.io/docs/usage/advanced/ 、https://getsops.io/docs/usage/identities/age/
- グローバルな秘密の保管・移行:
  - ユーザーは現在fishのグローバル設定にContext7 APIキーなどの環境変数を記述している。値や秘密を含む実ファイルは調査していない。
  - dotenvxは `run -f /absolute/path/to/file` でプロジェクト外の共通ファイルも利用できる。配置場所がグローバルであっても、秘密の注入は起動したコマンド単位に限定できる。
  - dotenvxは標準で既存の環境変数を優先する。移行時はfishの常時exportを外し、現在のセッションにも残らないようにする必要がある。具体的な移行対象は未確定。
  - 共通ファイル全体をロードすると、そのファイル内の他ツール用の秘密も同じコマンドへ渡る。
  - Q4:Bで共有の秘密ファイルは一つにまとめる方針に合意済み。
  - ユーザーはエージェントが毎回 `dotenvx run` を選んでツールを実行する必要があるかを懸念している。
  - Q5:Aで共通のグローバル鍵はエージェント起動時に自動注入する方針に合意済み。ツール単位の起動ラッパーはこの用途には導入しない。Q2:Aのプロジェクト／アプリ用秘密は引き続き必要なコマンド単位で注入する。
  - Q9:Aで共通ファイルのGit管理はしない方針に合意済み。`config/.config/.env.example` をテンプレートとし、実ファイルは `config/.config/.env`、参照先は `~/.config/.env` とする。
    - 初期暗号化と既存config.fishからの実際の秘密移行はユーザーが行い、エージェントは秘密の値を読まない想定。
    - Q11:AでmacOS Keychainによる復号鍵保管に合意済み。Keychainのlaunchd経由・非対話利用は未検証。
    - `.env.keys` ファイルへの切り替えは今回の合意に含めない。鍵のバックアップ方法はユーザー側の運用として未確定。
  - 出典: https://github.com/dotenvx/dotenvx/blob/main/README.md
- 暗号化は保管時の保護。復号した秘密や復号鍵をエージェントの環境変数に渡すと、エージェントおよび子プロセスから利用できる。
- 現在のファイルdenyは暗号化された `.env` や参照だけの `.env` も拒否する。注入の実行場所・ファイル名に合わせて限定的な調整が必要。暗号化ファイル・参照ファイルと秘密鍵を区別する。
- 比較時の評価（dotenvx採用方針に決定済み）: 1Password利用には `op run` + `op://` 参照、Git管理の `.env` 暗号化にはdotenvx、より広い設定形式やKMS連携にはSOPS。EnvironmentsのFIFO mountは互換性優先の今回の用途では優先しない。
- ホストプロセス操作・Macサービスを許可すると、別プロセスの環境やKeychainなどから秘密を利用できる場合がある。必要なコマンドだけへの注入は露出範囲を減らすが、承認済みの広いホスト連携のもとで完全な秘密隔離は保証しない。
- Q3で合意した削除対策の実装詳細:
  - 未合意の提案: エージェントごとのシェルaliasではなくPATH上の実行ファイルでrmのごみ箱化を共通化する。これは通常のコマンドの誤削除対策で、OSの強制制限ではない。
  - Q6:Bで現在の広い書き込み許可を維持し、さらに拡大してよい方針に合意した。作業先と必要な状態保存先に絞る推奨案は撤回。
  - Q7:AでHOME配下を原則読み書き可能にする方針に合意済み。
    - HOMEの広い追加許可はSafehouse標準のHOME内denyも再開放し得る。現行の読み取り保護・機密denyを維持するポリシー構成を確認する。
    - dotenvxの共通ファイル・起動ラッパー・sandboxポリシーなど、保護対象への個別制限も計画時に確認する。
  - Q8:Bで普段のターミナルにもrmのごみ箱化を適用する方針に合意済み。
    - 通常の掃除・ビルドなどの削除もごみ箱へ蓄積する。シェルaliasだけでは別シェル・非対話実行には行き渡らないため、実行経路を確認する。
    - gomiのごみ箱掃除・永久削除は通常のrm転送とは別経路で扱う。
  - gomi: ファイルをごみ箱へ移し、元パス情報を使って復元できる。設定は `~/.config/gomi/config.yaml` でdotfiles管理できる。通常のrmフラグに対応。永久削除用の `--prune` もあり、取得した実装では `-f` が確認を省略する。設定の `permanent_delete.enable: false` は `--prune` 全体を無効化する保証ではない。エージェントの通常削除とごみ箱掃除を分離する必要がある。
  - shell-safe-rm: macOSでは標準でAppleScript/Finder経由のごみ箱を使い、Put Backに対応。カスタムごみ箱・AppleScript無効時は手動復元。`SAFE_RM_SCOPE`、保護パターンに対応するが、READMEは保護パターン配下を含む親ディレクトリ全体の移動を防げないと明記している。
  - 両者とも `/bin/rm`、PythonやNodeの直接削除、`git clean` / `git reset --hard`、上書き・切り詰めは保護しない。aliasは別シェルや非対話実行へ継承されるとは限らない。
  - ごみ箱化だけでは読み取り保護にならない。OSの削除操作だけを禁止する案も、renameによるごみ箱移動や一時ファイル置換などとの互換性を検証せずには採用しない。
  - 出典: https://github.com/babarot/gomi 、https://github.com/babarot/gomi/blob/main/internal/cli/prune.go 、https://github.com/kaelzhang/shell-safe-rm
  - 公式READMEと実装を調査したのみで、削除・復元の実機テストやインストールはしていない。
- Q10:BでHermes gateway/dashboardへの新方針の適用に合意済み。
  - 現在のサービスラッパーはfishの設定を経由せず、bashから `mise ... safehouse ... hermes` を起動する。常駐サービスにもPATH・dotenvxによる注入を明示的に適用する必要がある。
  - launchd環境でのPATH・秘密注入・鍵取得の非対話利用を検証する。現在の `mise`・venv・Hermes固有環境・正規シャットダウン経路を保持する。
  - `command -v` ではdotenvxとgomiは現在のPATHに見つからなかった。インストール・実動作検証はまだ行っていない。
- 互換性ルールとファイル保護ルールの分割は未合意の提案。後段に保護ルールを置き、ファイル制限を一括で解除する `allow default` は使わない想定。
- Safehouseのネスト制約は権限緩和だけで解決できない。Chromium内蔵sandboxについて公式は `--no-sandbox` を要求している。
- Q12: ここまでの全体方針の最終確認待ち。確認後にdigを終了し、planスキルで実装計画を保存する。計画への再承認後にimplementスキルで実行する。
  - PATHラッパーの配置・rm互換性、Safehouseの保護対象とポリシー適用順、dotenvx起動処理は計画時に既存実装と公式仕様を確認して具体化する。
  - ごみ箱の自動掃除・永久削除の自動化は依頼されていないため導入しない想定。通常のrmとは別の手動操作として扱う。
  - 初期の秘密移行・Keychainへの実鍵登録・鍵のバックアップはユーザー側で行い、エージェントは秘密の値を扱わない想定。
  - 方針を満たせない検証結果が出た場合は相談し、秘密の保管方式や保護範囲を無断で変更しない。
