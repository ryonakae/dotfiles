# dig log: Nix から Brewfile・mise 中心の構成へ移行

## 目的・前提・制約
- Nix が現在の個人用 Mac 環境には大袈裟になってきたため、Brewfile + mise + 最小限のセットアップスクリプトへ移行し、導入・日常運用を簡素化する。
- 本セッションの dig 開始前の議論を取り込んだ。過去セッションの会話全文は参照しておらず、過去の判断は既存ログ・計画に記録された範囲だけを参照する。
- 関連記録: [Nix 導入](2026-10-03-nix-migration.md)、[ホスト設定](2026-10-05-nix-host-configuration.md)、[ユーザー向けセットアップ](2026-10-12-human-first-setup.md)、[Hermes 配置](2026-10-13-hermes-conditional-activation.md)、[ハイブリッド移行](../plans/archived/2026-10-07-hybrid-dotfiles-management.md)。これらは過去の記録で、現行実装と今回の合意を優先する。
- 現在、通常アプリは Homebrew、共通 runtime と通常設定・自作スキルの直接リンクは mise。Nix は OS 設定、導入宣言、Hermes、本体・plugin・外部スキルの一部に残っている。
- 保護設定、秘密・認証・memory・session・DB などを保持する。未知の実体を強制上書きしない。設定変更、実機適用、サービス操作、Nix 撤去の承認は区別する。
- dig 中は本ログのみ編集し、ユーザーの共通理解確認後に計画作成へ進む。最新 mise の利用は了承済みだが、この調査では更新・インストールをまだ行っていない。
- 開始時の既存変更: config/.claude/settings.json、config/.config/fish/config.fish、config/.config/ghostty/config、flake.lock。未追跡の .DS_Store（root/config/docs/nix）も保持する。

## 決定事項
- 実装後の方式変更: mise の Git Python backend は対象 fork の wheel ビルド禁止と両立しなかった。ユーザーは「前者の方式で」として、mise task から fork の標準 shell installer を呼ぶ方式を選択し、更新計画を `/implement` で承認した。初回だけ導入・別 task で明示更新という Q6 は維持する。以下の Git Python backend に関する調査記録は採用方式ではない。具体的な契約は[移行計画](../plans/2026-10-14-nix-to-mise.md) §4 を参照する。
- Q11: セットアップスクリプトは全体実行だけを用意する。アプリ・配置・macOS 設定などを選ぶ独自の部分実行機能は追加せず、部分操作は brew bundle や mise dot apply 等の標準コマンドを直接使う。よく使う操作はユーザー向け文書に記載する。
  - 出典: Q11 の A に対するユーザーの「a」。
- Q10: 今回の計画・実装の完了範囲に、この Mac での新方式への切替、Nix に依存しない動作確認、Nix 撤去までを含める。新旧の管理を長期間併存させることを目標にしない。
  - Nix の撤去は新方式の動作確認後の最後に行う。サービス操作・削除などは実行直前にも確認し、この回答を即時実行の承認としない。別 Mac の実機操作は含まない。
  - 出典: Q10 の A に対するユーザーの「a」。
- Q9: macOS 設定は現在の内容を再現する。mise で扱える項目は mise で管理し、非対応項目だけ pmset 等の macOS 標準コマンドを使う小さなスクリプトで補完する。独自の汎用設定管理基盤は作らない。
  - 出典: Q9 の A に対するユーザーの「a」。
- Q8: fish・Yazi の外部 plugin は、外部スキルと同様に通常セットアップ時の最新版への更新を許容する。固定版維持を要件にしない。取得・配置は各 plugin の標準的な導入方法に合わせる。
  - 対象は現行の fish bobthefish/fzf、Yazi git/smart-enter/full-border。本体との互換性が常に保証されるとは扱わず、問題発生時に個別対応する。
  - 出典: Q8 の A に対するユーザーの「a」。
- Q7: 共通 Node/Python/Ruby/Bun は現在の具体的なバージョン指定を維持する。セットアップでは指定版を導入し、更新は別途行う。プロジェクトごとの mise 設定は変更しない。
  - 理由: 既に mise 管理のため、Nix 撤去とランタイムのバージョン変更を分離する。
  - 出典: Q7 の A に対するユーザーの「a」。
- Q6: Hermes は通常セットアップでは未導入の場合だけ ryonakae/hermes-agent の ryonakae ブランチから導入する。導入済み Hermes の更新は別途明示的に行い、セットアップで自動更新しない。サービスの自動停止・再起動も追加しない。
  - 理由: 常駐サービス本体の更新と、他のアプリ・設定の適用を分け、再起動タイミングを管理できるようにする。
  - 出典: Q6 の B に対するユーザーの「b」。
- Q5: Brewfile から外したアプリは自動削除しない。不要になったものだけ宣言から外し、対象を指定して標準 brew uninstall で削除する。セットアップへの cleanup 組込みや、独自の削除候補管理操作は追加しない。
  - 出典: Q5 の A に対するユーザーの「a」。
- Q4: セットアップ時は、選択した Brewfile の不足分の導入に加え、インストール済みアプリの更新も標準 brew bundle に任せる。通常セットアップに --no-upgrade は付けない。
  - 出典: Q4 の B に対するユーザーの「b」。
- Q3: 適用する構成は毎回すべて明示する。例えば setup default private のように指定し、private/work を選んでも default を自動追加しない。private だけの適用も許容する。コマンド名・引数構文はまだ例示。
  - 理由: ユーザーは明示指定のほうが分かりやすいと判断した。
  - 出典: Q3 に対する「bの方が分かりやすい」。
- Q2: 外部スキルは必要なものだけ配置先を明示する。取得元リポジトリに追加されたスキルは自動で利用対象にしない。選択済みスキルの本文は Q1 の方針で更新する。
  - 自作スキルは既存の glob 配置を継続する。外部スキルを全件自動配置するための独自優先順位判定は追加しない。
  - 出典: Q2 の A に対するユーザーの「a」。
- Q1: 外部スキルは取得元のブランチを追跡し、通常のセットアップ時に最新版へ進むことを許容する。復元用コミットの固定・記録は要求しない。
  - 理由: 固定版の維持より、単純な管理と最新版への追従を優先する選択。
  - 出典: Q1 の B に対するユーザーの「b」。
- Nix 維持を前提にせず、Brewfile + mise + 最小限のセットアップスクリプトへ移行する方向で設計する。
  - 理由: Nix の運用負担を減らす。Nix の仕組み自体を別の独自基盤で再現しない。
  - 出典: ユーザーの「Nixは、ちょっと大袈裟」「ok, その方向で詰めましょう」。
- Homebrew は mise のパッケージ管理へ寄せず、Brewfile を正本にして標準 brew bundle をスクリプトから実行する。default + private のように複数ファイルを選択して実行できる構成にする。
  - 出典: dig 前のユーザー提案と、その方向への合意。
- 管理者パスワードは原則として最初の1回にまとめ、実行中だけ sudo の標準認証キャッシュを維持する。パスワード保存、sudoers 変更、スクリプト全体の root 実行は採用しない。
  - App Store 認証、ベンダー独自認証、macOS 権限承認まで1回に集約できる保証はしない。
  - 出典: ユーザーの「今やってるみたいに、パスワードは最初の1回だけ」と、その後の方式説明への方向合意。
- macOS 設定は mise で管理する。非対応項目は標準コマンドによる小さなスクリプトで補完する方針が Q9 で確定。個別分類は未完了。
  - 出典: ユーザーの「macosの設定はmiseで管理できるなら、それでいい」。
- 手元の mise は最新版へ更新してよい。
  - 出典: ユーザーの明示的な了承。
- Hermes は mise で ryonakae/hermes-agent の ryonakae ブランチを導入する方針。本家や fork の別ブランチへ置き換えない。
  - 出典: ユーザーの取得元・ブランチの明示と、その方式への合意。
- Hermes の追加依存の一致、CLI 以外の機能・資材の網羅的確認は移行の前提条件にしない。問題が出たら修正する。Nix 固有の voice 除外を無条件に再現しない。
  - 出典: ユーザーの「1,2は気にしないで良い。また修正すればいいから」。
- Hermes の Safehouse wrapper と gateway/dashboard の起動経路は Nix 参照から mise 管理の実行先へ変更する。サービスから正しい実行先を利用できることを確認する。保護設定と fork 標準の起動・停止方式を維持し、設定適用に自動停止・再開を追加しない。
  - 出典: ユーザーの「3は、修正が必要ですね」と、その後の整理への「ok」。
- 自作スキルは現在の mise dotfiles 管理を継続する方向。config/ を正本とし、共通・Claude 向け glob と Git 追跡ファイルの直接リンクを利用する。
  - 出典: 現行 mise.toml の確認と、全体の方向合意。

## 対象外
- この dig 中の実装、パッケージ更新・導入、実機適用、サービス操作、Nix の削除。
- Hermes の機能網羅性や Python 依存全体の厳密な固定を、移行可否を決めるゲートにすること。
- 秘密・認証・実行時データの移行や削除。

## 未決・保留
- 外部スキル: mise bootstrap.repos で取得し、dotfiles で選択配置する方式を具体化する。ブランチ追跡・セットアップ時の更新許容は Q1、必要なスキルだけ明示配置する方針は Q2 で確定。現行の自作優先・Claude 専用例外と二重所有回避を配置宣言へ反映し、取得元ブランチ・スキルのパスは実装前に調査する。
  - 調査: repos の ref はブランチ・タグ・完全 SHA。ブランチ指定では通常 apply でも更新を取り込み得る。変更済み checkout は保護され、宣言削除だけでは checkout を削除しない。
  - 参考: https://mise.jdx.dev/bootstrap/repos.html
- Hermes: 通常セットアップは未導入時だけ導入し、本体更新は別操作にする方針が Q6 で確定。mise の標準操作でこの境界を満たす具体手順、安定した起動先、plist の生成・配置方式を詰める。稼働中サービスの自動停止・再起動は追加しない。
  - 調査: Python backend は Git ブランチ指定と extras に対応。Git ソースは依存全体の graph lock ではない。インストール動作は未検証。
  - 参考: https://mise.jdx.dev/dev-tools/backends/pypi.html
- Brewfile: default/private/work の具体的な内容分割を現行宣言から移す。適用構成の全件明示は Q3、通常セットアップでの導入・更新は Q4、自動 cleanup をせず対象指定で削除する運用は Q5 で確定。
- setup のコマンド名・実装言語、途中失敗後の再実行、新規 Mac の Homebrew/mise 導入順序を計画時に具体化する。入口は Q11 により全体実行のみ、対象構成は Q3 により全件明示。sudo キャッシュ維持は入口へ集約し、既存の失敗時中止・自動再試行なしの方針を維持する。
- macOS 設定の対応範囲を調査し、mise と補完スクリプトに分類する。非対応項目を手動へ戻さず現在の設定を再現する方針は Q9 で確定。ホスト差分の表現を具体化する。
- 共通 Node/Python/Ruby/Bun の指定版維持・別途更新は Q7 で確定。Hermes の初回のみ導入という Q6 の境界と合わせ、setup 内の mise 操作を具体化する。
- fish・Bash・mise・usage の供給元、Nix 初期化の撤去、ログインシェル切替。fish/Yazi plugin の通常セットアップ時の更新許容は Q8 で確定し、取得・配置の具体方式は標準手順を調査して決める。
- 実機切替からこの Mac の Nix 撤去までを今回に含める方針は Q10 で確定。既存 Home Manager 所有リンクと nix-homebrew の引渡し、ログインシェル・起動経路の切替、daemon/store/profile 等の撤去対象・手順を調査する。Nix 非依存の動作確認後に撤去し、実操作直前の承認を分ける。
- 現行 AGENTS.md 等の「自前 Brewfile 禁止」「アプリ一覧は Nix」などは今回の方向に合わせて計画・実装時に更新する。dig 中には変更しない。
- 設計ツリーのユーザー選択は Q1〜Q11 で整理済み。更新方針、取得・選択配置、構成選択、OS 設定補完、実行入口、実機撤去範囲の共通理解を Q12 で確認済み。未確認の技術詳細は上記のとおり残し、計画時にコード・公式資料から解決する。標準機能で合意した方針を満たせないと判明した場合は再相談する。Hermes 依存・機能確認の免除は再質問しない。
- Q12: ユーザーの「a」により、Q1〜Q11 と開始前の合意を共通理解として dig を完了し、実装計画の作成へ進むことを承認された。計画承認前の実装・実機適用は行わない。

## 撤回・置換済み
- Q1 の推奨案だった外部スキルのコミット固定・明示更新は不採用。過去の Nix 導入時の外部スキル固定要件も、今回の移行ではブランチ追跡へ置換する。
- 過去の「Nix を構成管理の中心にする」「Homebrew の一覧を Nix に置く」「自前 Brewfile を作らない」方針は、今回の移行設計では Brewfile + mise 中心へ置換する。現行コードはまだ変更していない。
- アシスタントが挙げた Hermes の追加依存・機能網羅性の事前検証を重い障害として扱う姿勢は撤回。起動先の修正を必要作業とし、機能上の問題は発生時に修正する。
- 外部スキルのために現在の Nix カタログ・専用 lock の仕組みをそのまま再実装する前提は置かない。
